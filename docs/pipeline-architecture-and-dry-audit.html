rlm-bmdx turns uploaded dose-response data into a structured NIEHS toxicology report. This document explains the report-generation pipeline — the structure→data→render→output core that recent work touched and that ADR-0003 will refactor — and audits it for duplication and uncleanliness.

Scope note. The repo is ~100 Python files; this goes deep on the rendering pipeline with a one-screen map of the rest. Citations are file:line, verified against the rebuilt rlm-code index at commit f4676bd / e6e5979 (2026-05-27).

Scope

Six subsystems make up the app. This report covers the last row in depth; the others are mapped for orientation in §1.

2a · document_tree.py — the single source of truth

DOCUMENT_TREE is a hand-written tree of DocNodes (document_tree.py:44). A node carries id, node_type, level, title, children, and data-binding keys (data_key, narrative_key, methods_key). Nothing structural is hardcoded downstream — heading hierarchy, ordering, table numbers, and the front/body boundary all derive from a tree walk:

  • compute_table_numbers (:447) assigns table numbers positionally by walking the tree — never user-provided.
  • first_body_node_id + FRONT_MATTER_NODE_TYPES (:425) define where roman front-matter numbering switches to arabic body numbering.
  • serialize_tree (:567) emits the tree as plain dicts (node type under key "type") for the frontend.
  • find_node (called in 23 places) is the universal "jump to a node" primitive.

Node types: cover, title-page, front-matter, narrative, heading-only, appendix, tables-list, narrative+tables, table, incidence-table, bmd-summary, genomics-section. Two are already generated components — tables-list (a List of Tables built by walking the tree) — the working precedent for the ADR-0003 ToC.

2b · render_capabilities.py — the type→capability catalog

A single dict CAPABILITIES_BY_TYPE maps each node_type to NodeCapabilities(orientable, breakable, editable) — the one coupling point between document and rendering semantics, and the embryo of ADR-0003's component catalog. background_server.py calls annotate_capabilities(serialize_tree()) so both the injected window.__DOCUMENT_TREE__ and /api/document-tree carry capability flags; the frontend reads them off the tree rather than re-encoding the mapping in JS.

Two keys, two jobs. Capabilities are keyed by node type (the catalog); user choices (orientation, future breaks/edits) are keyed by node id (a per-session overlay). One-way dependency: overlay → template.

2c · report_data.py — marshal (scaffold-then-overlay)

marshal_export_data(body) (:180) turns web session state into the render-ready dict. The pattern is clean in concept: scaffold_report_data (:972) builds the complete report dict shape (every section, with placeholders), then marshal_export_data overlays real approved content on top (:213 calls the scaffold, then patches). A sparse session still renders a full scaffolded report, and the dict shape is single-sourced in the scaffold — not re-declared. It also already builds ToC metadata via _build_toc_entries (:1280) and methods sections via _build_methods_sections_from_tree (:937), both tree-driven. (The function itself is a 585-line god function — see finding #2.)

2d · html_generator.py / latex_generator.py — two backends, one tree

Both renderers do the same thing in two output languages: walk DOCUMENT_TREE + the data dict, dispatch each node on its node_type to a handler, concatenate the chunks. generate_html produces a self-contained HTML doc with Paged.js (a CSS Paged Media polyfill) that paginates into printed-page sheets in the preview iframe; generate_latex produces report.tex against niehs.cls for an Overleaf .zip. Two surfaces only — no PDF, no Typst. The handler sets are parallel (_render_narrative, _render_apical_table, _render_bmd_summary, _render_genomics_section, …), one pair per node_type.

2e · frontend (web/js/*)

The navigation panel is a projection of the serialized tree (renderNavFromTree in layout.js); clicking a node sets activeSection and scrolls the side preview pane (ensureFullPreview in export.js, the single live preview surface after the recent dead-code removal). The orientation toggle is enabled per node.capabilities.orientable and writes a per-id overlay that flows back through buildExportPayload to both renderers. (Per ADR-0003 we just renamed this subsystem off "toc" → "nav", freeing "ToC" for the document component.)

3 · Cleanliness & DRY findings (prioritized)

#1 — Renderer triplication + silently-drifting dispatch highest

html_generator._walk (:1022) and latex_generator._walk (:904) are the same recursive algorithm copy-pasted: identical dispatch line, identical if chunk: guard, identical child-recursion tail, and a byte-identical orientation gate:

if (data.get("orientations", {}).get(node.id) == "landscape"
        and capabilities_for(node.node_type).orientable):

html_generator.py:1042-1043 ≡ latex_generator.py:923-924 — only the wrapper string differs (<div class="landscape-block"> vs \begin{landscape}). Both were written this session.

Worse, the two _DISPATCH registries already drift: HTML registers cover/title-page (:1002-1015, 12 entries); LaTeX does not (:886-897, 10 entries — intentional, it uses \maketitle). The comment at html_generator.py:999-1001 claims they "stay in lock-step," which is now false.

Risk. The lock-step contract is enforced only by a comment. Add a new node_type to one renderer and forget the other, and the section renders in the HTML preview but silently becomes [Section pending] in the Overleaf export — a desync you'd only catch on Overleaf.

Around this sit a cluster of parallel helpers with shared contracts (and even shared docstrings) as separate copies: _heading (html:358/latex:145), _render_paragraphs (html:371/latex:159), _pending/_pending_placeholder (html:383/latex:172), _render_unimplemented (html:987/latex:855), the front/body split loop (html:1196/latex:1093), and the running_header → title → "5dToxReport" fallback (html:1213/latex:1080). _esc/_escape_latex are correctly format-specific (not a defect).

Fix → this is the ADR-0003 win. One tree-walker + one shared dispatch registry, parameterized by a per-format backend providing six primitives (escape, heading-wrap, paragraph-wrap, pending-placeholder, orientation-wrap, anchor-emit). That removes #1, the gate duplication, and most of the helper cluster in one move.

#2 — marshal_export_data is a god function (585 lines) high

report_data.py:180-765 is one linear procedure with ~10 distinct phases (scaffold init, metadata overrides, front-matter, background+refs, methods, a ~130-line abstract-assembly block, apical-sections loop, narratives/BMD, genomics, summary+ToC+filter). It mixes request parsing, disk I/O mid-function (reads session cache files at :389 and :696), domain math (LLE at :628), tree queries, and dict assembly.

Fix. Same shape as the process_integrated god function ADR-0002 targets — extract _overlay_<phase>(data, body) helpers with a golden-snapshot test as the regression oracle.

#3 — Duplicated full-title derivation (byte-identical) high

The study title is built in two places, copy-pasted:

running_header_name = ta["forms"]["running_header"]["text"]
full_title = (f"In Vivo Repeat Dose Biological Potency Study of "
              f"{running_header_name} in Sprague Dawley Rats")

report_data.py:233-239 (in marshal_export_data) ≡ report_data.py:1016-1020 (in scaffold_report_data).

The hardcoded "…in Sprague Dawley Rats" phrasing is duplicated even though strain is already a configurable field — change one and the two paths diverge.

Fix. Extract _build_full_title(ta).

#4 — Duplicated genomics-cache read medium

The same sessions/<dtxsid>/_cache_genomics_*.json glob-and-load (with silent exception-swallowing) appears at report_data.py:386-395 and :692-702. Two disk reads per call; error handling can drift.

Fix. Extract _load_genomics_cache(dtxsid).

#5 — Page-number margin-box style duplicated 4× medium

The exact declaration

font: 11px -apple-system, ..., Arial, sans-serif;
color: #4a5568;

is repeated in three @page rules and the running-header builder: html_generator.py:249-250, :267-268, :291-292, and :1095-1096. Change the footer/header typeface (e.g., to match the Overleaf font) and you must hit all four.

Fix. A single _MARGIN_BOX_FONT constant. (Minor sibling: _document_skeleton ≈ _fragment_skeleton, html:1100/:1128, share shell boilerplate.)

4 · Bottom line

The architecture is sound and disciplined where it counts: the tree is genuinely the single source of truth, the scaffold-then-overlay pattern single-sources the report shape, and render_capabilities already centralizes the type→capability mapping. The cleanliness debt is concentrated in two well-understood spots — the copy-pasted dual renderers (finding #1, the sharpest hazard because drift is silent) and the marshal_export_data god function (#2). Findings #3–#5 are quick, safe extractions.

The encouraging part: finding #1 is the strongest argument for ADR-0003's design. A shared tree-walker + catalog-driven dispatch + per-format backend is exactly the consolidation that eliminates the renderer drift — and the catalog you'd build for it is the same catalog ADR-0003 needs. The refactor pays down the biggest debt as a side effect rather than as separate work.
