What the integration step produces, why integrated.json is not a self-contained ready-store, and the three on-disk sources report content actually reads from. File:line references are to the current tree.

0 · The one thing to know

Common misconception: "integrated.json is the application's ready-store — everything downstream queries it."
Reality: integrated.json is the merged apical dataset and the declared single source of truth, but it is not self-contained. The wide-format pivot inside it discards per-animal metadata, so report content also reads sidecar JSON files (for the per-animal detail) and the gene-expression .bm2 (genomics has its own extraction path). Integration is a merge + normalize step, not a "load everything into one queryable blob" step.

So there are really three live data sources the compute stage reads — see §4. And the "query engine" (the processing pipeline) sits upstream of the caches that filtering later projects — see §7.

1 · The data pipeline, end to end

A session moves through a phase machine (ADR-0014); the data stages are:

raw study files            (.bm2, .txt/.csv, .xlsx, .sidecar.json)  →  sessions/<dtxsid>/files/
   │  validate_step         re-fingerprints every file, cross-validates → validation_report.json
   │  resolve_step          user picks a winner when platforms conflict → precedence.json
   │  confirm_metadata_step writes platform/data_type headers into txt/csv
   ▼
INTEGRATE  (integrate_step → bmdx_pipe.integrate_pool, Java)          →  integrated.json  (+ _category_lookup.json)
   │                                                                      + *.sidecar.json  (written during xlsx/csv → pivot)
   ▼
APPROVE    (generate_animal_report_step)                             →  animal_report.json
   ▼
PROCESS    (process_step → run_process)   reads integrated.json      →  _cache_*.json  (the report content)
                                          + sidecars + gene .bm2

Key point: integration (the "I" step) does the file-level merge into integrated.json. The expensive report content — NTP stats, BMDS modeling, genomics, narratives — is produced later, by PROCESS, and cached as _cache_*.json. Those caches, not integrated.json, are what the report and the filtering layer consume at render.

2 · What integration actually produces

integrate_step (workflow/steps.py) gathers the validated pool + coverage matrix + user precedence + chemical identity, then delegates to integrate_pool (bmdx-pipe/src/bmdx_pipe/pool_integrator.py). Per its docstring, for each platform it:

  1. uses the user-chosen file if a conflict was resolved;
  2. else prefers .bm2 (has BMD results) → txt/csv → xlsx;
  3. converts .xlsx to pivot .txt (and long-format CSVs too) — writing a sidecar JSON alongside each;
  4. calls the Java IntegrateProject to merge everything with native BMDExpress classes;
  5. reads the JSON back and attaches _meta + _category_lookup.

The result is a BMDProject JSON with top-level keys: doseResponseExperiments (the primary data), _meta (source-file provenance, imputed cells, clinical-obs file paths, xlsx rosters), plus precomputed Java result lists (bMDResult, categoryAnalysisResults, …).

Two things it is NOT: (1) it is not small — the reference session's integrated.json is ~68 MB, dominated by the per-animal response arrays, so it is never shipped to a browser (that is what the slim /api/integrated-tree and /api/integrated-summary endpoints are for); (2) it is not the computed report — no NTP statistics, no fitted BMDs for the apical tables, no genomics gene-set tables. Those are derived by PROCESS.

3 · The pivot data-loss problem — why sidecars exist

When integrate_pool converts a long-format study file to the wide-format pivot the Java integrator expects, it collapses many per-animal rows into one row per dose group. That pivot discards per-animal detail (pool_integrator.py:694):

  • Selection — Core Animals vs Biosampling Animals,
  • Observation Day (e.g. SD0 vs SD5) and the Terminal Flag,
  • Raw per-animal values, including non-numeric "NA".

That metadata is load-bearing for the report: correct N counts (Core Animals only), dose groups where animals died, attrition footnotes, terminal-day selection. So the same conversion writes a sidecar JSON next to each pivot file capturing exactly what the pivot dropped:

{
  "source": "body_weight_truth_male.csv",
  "platform": "Body Weight",
  "sex": "Male",
  "animals": {
    "101": {
      "dose": 0.0,
      "selection": "Core Animals",
      "observations": [
        {"day": "SD0", "endpoint": "Body Weight", "value": "285.1", "terminal": false},
        {"day": "SD5", "endpoint": "Body Weight", "value": "300.3", "terminal": true}
      ]
    }, ...
  }
}

Consequently the Body Weight, Organ Weight, Tissue Concentration, and Clinical Observations tables are built from the sidecars (via build_*_from_sidecar), not from the pivoted rows in integrated.json — because the sidecar has the per-animal truth the pivot lost. Reading the sidecars is sanctioned (CLAUDE.md invariant #1), not a bypass.

4 · The three live data sources at PROCESS time

run_process (pipeline/process_integrated.py) and its helpers read from three on-disk sources:

SourceRead viaFeeds
integrated.json (BMDProject) store.get_integrated() (process_integrated.py:1133) NTP stats → platform_tables (the apical dose-response data), category lookup
*.sidecar.json find_sidecar_paths + build_*_from_sidecar (process_integrated.py:701, 785) Body Weight, Organ Weight, Tissue Concentration, Clinical Observations tables; mortality/attrition
gene-expression .bm2 export_genomics (Java) (processing_helpers.py:946) Genomics: per-gene BMD + GO categories. Its OWN path — gene expression has thousands of probes and is not run through the NTP pivot.

The genomics .bm2 read is why gene-expression experiments are stripped from the dict that feeds NTP stats (_strip_gene_expression, processing_helpers.py:16) — apical and genomics take entirely separate compute paths.

5 · Cache lifecycle & invalidation

PROCESS writes the report content as per-stage caches under sessions/<dtxsid>/: _cache_ntp_*, _cache_sections_*, _cache_bmds_*, _cache_bmd_summary_*, _cache_genomics_*, _cache_charts_*, _cache_methods_*. Each stage's cache key is a hash of only the inputs that affect that stage, so an unrelated change doesn't invalidate everything.

Integration is the hard reset. integrate_step deletes every _cache_*.json after a (re)integration (workflow/steps.py) — the input data changed, so all derived content is stale. This is why re-integrating forces a full ~8-minute recompute, while re-processing with the same integration is cheap (cache hits).

store.get_integrated() itself is memory-cached (a per-process pool) but falls back to reading integrated.json from disk, schema-validated every load — so PROCESS works even in a cold process after integration.

6 · The source-of-truth hierarchy

When two sources could answer the same question, resolve in this order:

  1. Sidecar JSON — for anything per-animal (selection, terminal flag, raw values, N counts, attrition). The pivot lost this; the sidecar is authoritative.
  2. integrated.json — for the merged apical dose-response data, provenance (_meta.source_files), and the precomputed Java BMD/category results.
  3. gene-expression .bm2 — for genomics (per-gene BMD, GO categories), via export_genomics.

Never bypass to read raw .txt/.csv/.xlsx directly in report code. If data is missing, fix the integration step — don't add a bypass (CLAUDE.md invariant #1).

7 · How this relates to the filtering system

The filtering layer is not a query engine over integrated.json. The chain is:

integrated.json + sidecars + gene .bm2   →   run_process (compute)   →   _cache_* supersets
                                                                              │
                                       filters / version projection  ─────────┘   applied HERE (read/render)

PROCESS is the thing that reads the raw sources and produces the superset report content. Filters and report versions operate one step downstream, projecting those cached supersets — they never touch integrated.json. See docs/filtering-system.html for that layer.

So the corrected mental model: integrated.json is the merged apical source-of-truth (plus its sidecar and gene-.bm2 companions); PROCESS is the compute step that turns those into cached report content; filtering is a projection over the caches. "Integrated" is an input to compute, not a ready-to-serve store.
