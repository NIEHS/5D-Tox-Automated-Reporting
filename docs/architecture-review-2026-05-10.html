Architecture Review

rlm-bmdx — Deepening Opportunities

2026-05-10 · main branch 4c09d19 · 8 candidates

Executive summary

rlm-bmdx is now mature enough that most of the friction we encounter is not in writing new features but in landing them safely. As the codebase has grown — about 41,500 lines across the Python and JavaScript layers — a handful of files have absorbed responsibilities that originally belonged elsewhere. Most are still working correctly. None are in crisis.

What has changed is the cost of changing them. That cost shows up in the places worth measuring: the time it takes to wire a new narrative section, the time it takes to add a new chemical’s report, and our confidence that a fix in one area hasn’t quietly broken another. The pattern is well understood — most codebases this size encounter it once the original shape has been stretched past its initial design assumptions.

This document is a structured look at where that stretching has concentrated. It identifies eight specific places where the underlying code shape no longer matches what the project has become. Several are small, contained improvements that can be landed and verified in a single afternoon. A few are larger and would warrant careful validation before starting. One in particular — the contract between rlm-bmdx and the upstream bmdx-pipe project — would, if addressed, meaningfully reduce a class of intermittent errors we currently rediscover by accident.

The practical question is which to pick first. Nothing below is urgent in isolation; together, they are the difference between a codebase that keeps pace with the science and one that gradually slows it down.

Eight architectural friction points found by walking the codebase. Each is a candidate deepening opportunity — somewhere a shallow module could become a deep one, or a leaky seam could be made explicit. Ranked roughly by impact.

No new interfaces are designed in this document. The next step is to pick one candidate and grill the design. Cross-cutting candidates (#1, #3, #4) should not be started in parallel — the lesson from the earlier domain-model refactor was that one-at-a-time, validated end-to-end, beats two-at-a-time half-validated.

Vocabulary used in this document
Module
Anything with an interface and an implementation.
Interface
Everything a caller must know — types, invariants, error modes, ordering, config.
Depth
Leverage at the interface. Deep = a lot behind a small interface. Shallow = interface ≈ implementation.
Seam
Where an interface lives — a place behaviour can be altered without editing in place.
Deletion test
Imagine deleting the module. If complexity vanishes, it was a pass-through. If it concentrates elsewhere, it was earning its keep.
Locality
What maintainers gain from depth — change, bugs, knowledge concentrated in one place.
Leverage
What callers gain from depth — a small interface that does a lot.

The eight candidates

№ 1

pool_orchestrator.py is six modules in one

High confidence
Files pool_orchestrator.py (3488 lines)
Problem

One file owns fingerprinting, validation, conflict resolution, integration, per-platform section-card building, and genomics extraction. Validation is interleaved with I/O inside HTTP-endpoint handlers (api_run_lightweight_validation and friends), so testing “given these fingerprints, what does validation say?” requires mocking the endpoint or spinning up the full pipeline.

Hypothesis

God object. Deletion test: the module is not a pass-through — removing it would scatter complexity across session_routes.py, llm_routes.py, and the table builders. So the orchestration is earning its keep, but it’s earning it as six modules pretending to be one. Each phase has the depth to stand alone; together they form a hub nobody can change without re-reading 3500 lines.

What deepening looks like

Separate phases into independently-callable modules (validation, integration, section-card extraction, genomics extraction). Each becomes a deep module with a small interface (input data → output report). The orchestrator shrinks to a coordinator.

Benefits

Locality: fingerprint logic changes don’t risk breaking section-card building. Leverage: a validate_pool(fingerprints, conflicts) -> Report interface is a 10-line unit test instead of a FastAPI integration test. Cross-link: same shape as the earlier domain-model refactor (committed but not validated end-to-end), so the cross-cutting-refactor constraint profile applies.

№ 2

ToxKBQuerier is a shallow wrapper — .con.execute() leaks through

High confidence
Files interpret.py (lines 88–207); upload_routes.py (line 646); other call sites
Problem

The class promises a typed-query interface over bmdx.duckdb, but ~30 callers reach through kb.con.execute("SELECT ...") directly. The real interface is SQL; the class is decoration.

Hypothesis

Shallow wrapper. Deletion test: if you delete ToxKBQuerier, callers move from kb.con.execute(...) to duckdb.connect(path).execute(...) — three extra characters. Complexity concentrates nowhere; the wrapper is a pass-through. It’s earning nothing right now. That doesn’t mean the seam is wrong — it means the seam exists but no caller honours it.

What deepening looks like

Turn it into a real DAO. Define a small set of typed query methods (e.g. chemical_summary(dtxsid), paper_organs_for(dtxsid)); make .con private; force schema brittleness to live in one file. Per the knowledge-base notes, bmdx.duckdb schema is a cross-project contract — concentrating it in one DAO is the natural seam.

Benefits

Locality: a schema change (bmdx-pipe rebuilds the DB with renamed columns) breaks one file instead of 30. Leverage: narratives can mock ToxKBQuerier instead of mocking duckdb. Tests: narrative generation gets unit-testable without a DB fixture.

№ 3

Narrative generation is reinvented per section — no shared seam

High confidence
Files background_writer.py, unified_narrative.py, genomics_narratives.py, llm_routes.py; the build_*_intro/findings quartet in methods_report.py (lines 2418, 2498, 2641, 2706)
Problem

Each narrative type implements “build context → render prompt → call LLM → parse → validate → return prose” from scratch. The four methods_report.py functions have nearly identical shape (same return type, same data flow) with no shared base. When the customer asks for a fifth narrative type, the path of least resistance is copy-paste.

Hypothesis

Missing seam — same operation, no module. Deletion test: delete any single narrative module and complexity reappears at exactly one caller. The four narrative modules are deep individually but collectively shallow because they don’t compose.

What deepening looks like

A single Narrative module — context-builder + prompt-template + LLM-call + parse pipeline — where each section type is a small adapter. By the “two adapters = real seam” rule, you already have at least four, so the seam is real. The style-learning system in style_learning.py likely wants to hook into this single seam too.

Benefits

Locality: prompt-engineering improvements (caching, retry policy, citation grounding) land in one place. Leverage: adding a sixth narrative type costs an adapter, not a module. Tests: narrative-shape tests run without an LLM (mock the adapter).

№ 4

integrated.json shape is implicit — no schema at the rlm-bmdx ↔ bmdx-pipe seam

High confidence
Files pool_orchestrator.py (line 91 caches _integrated_pool: dict[str, dict]); every consumer
Problem

Architectural invariant #1 says “integrated.json is the single source of truth,” but the shape of that truth lives in a Java class in bmdx-pipe. rlm-bmdx loads it as untyped dict and the contract is implicit. If bmdx-pipe schema drifts (e.g. renames bmdl → bmd_lower), rlm-bmdx finds out at runtime, often via a confusing KeyError deep in a table builder.

Hypothesis

Missing schema at a real seam. The seam between rlm-bmdx and bmdx-pipe is the most important seam in the project — but it has no contract module on the rlm-bmdx side.

What deepening looks like

A BMDProject Pydantic model in rlm-bmdx that validates on load. Becomes the canonical “this is what we expect from bmdx-pipe.” Memory note project_bmdx_pipe_migration.md records that these are separate projects (not a migration), which makes the schema contract more important, not less — you can’t refactor across the seam.

Benefits

Locality: schema mismatches surface at one assertion at load time, not 12 mysterious downstream failures. Leverage: type-checking in IDEs and tests across all consumers. Tests: fixtures become typed, not untyped dicts.

№ 5

Python → Typst data dict is an implicit, undocumented contract

High confidence
Files report_pdf.py (lines 22–80, build_report_pdf); report.typ; every caller that builds the data dict
Problem

build_report_pdf(data: dict) passes a dict to Typst via stdin. The expected keys (foreword, background, methods, bmd_summary, abstract.sections[].label, …) are documented only in the docstring. Callers assemble the dict by hand from sidecars and table outputs. A renamed field surfaces as an opaque Typst compilation error.

Hypothesis

Same shape as #4 (missing schema at a seam) but at the output boundary. The seam between Python and Typst is real (two languages, subprocess, stdin/stdout), so the contract should be explicit.

What deepening looks like

A Pydantic model for the PDF data envelope; build_report_pdf accepts the model, not a dict; assemblers must construct the model. report.typ is documented as “this is what consumes the model.”

Benefits

Locality: adding a section means one model edit + Typst edit, not “find every place that builds the dict.” Tests: golden-test the dict shape independent of running Typst.

№ 6

Sidecar loading is scattered — no SidecarStore seam

Medium-high confidence
Files table_builder_common.py (find_sidecar, load_sidecar); pool_orchestrator.py (lines ~1953, 2053); each *_table.py
Problem

Sidecars preserve per-animal metadata that integrated.json discards (Selection, Observation Day, Terminal Flag, raw values). They’re loaded ad-hoc via shared helpers from both table builders and the orchestrator. The discovery logic (file naming, parsing) lives in the helpers, but every caller knows the convention by virtue of importing those helpers.

Hypothesis

Leaky seam. Sidecars are an implementation detail of “per-animal data sources,” but the orchestrator reaches around the table builders to load them for narrative generation. Two consumers, no module — by the “two adapters = real seam” test, this seam is required but absent.

What deepening looks like

A SidecarStore that owns discovery, parsing, and a typed data interface. Table builders and orchestrator both depend on the store, not on filenames.

Benefits

Locality: sidecar naming changes (the unresolved study-day data-model question) edit one file. Leverage: store can transparently fall back to integrated.json when sidecars are absent, hiding the pivot-data-loss problem behind a clean interface. Tests: sidecar loading is testable in isolation.

№ 7

session_store.py exposes helpers, not a SessionStore module

Medium confidence
Files session_store.py; session_routes.py
Problem

session_store.py exports loose helper functions (save_section, delete_section, load_style_profile, …). session_routes.py calls them and assumes the returned dicts have specific shapes the JS UI expects. There’s no SessionStore class with a typed contract, no Pydantic models for what’s saved/loaded.

Hypothesis

Helpers, not a module. Deletion test: delete session_store.py and the helpers reappear inline in session_routes.py — barely worse, which is the diagnostic for shallowness. The seam exists in name but adds little leverage.

What deepening looks like

A SessionStore class with typed session-data models; routes hold a SessionStore instance. Tests can use an in-memory store. Aligns with the “state derivation, never imperative” rule: an explicit store makes the derivation rule enforceable.

Benefits

Locality: schema for “what’s a saved section” lives in one place. Tests: routes become unit-testable without disk I/O.

№ 8

DocNode tree → table-numbering → narrative is a fragile three-phase coupling

Medium confidence
Files genomics_narratives.py (lazy import at line 76 of compute_table_numbers, find_node); document_tree.py
Problem

Architectural invariant #2 says the DocNode tree drives all structure, but the narrative builder reaches into the tree at runtime to compute table numbers for intro prose (“Tables 4–7 below…”). This requires (a) the tree exists, (b) table numbers are computed, (c) then narratives can be built — and the lazy import exists to break a circular dependency.

Hypothesis

Coupling to presentation. Narratives shouldn’t know about numbers; they should know about references the renderer resolves later. The lazy import is the smell.

What deepening looks like

Narratives emit reference tokens (e.g. {table:liver-bmd-summary}); a renderer pass replaces them post-tree-walk. The narrative module no longer imports document_tree.

Benefits

Locality: re-ordering sections in the tree never re-runs narrative LLMs. Leverage: same narrative reusable in HTML and PDF without re-resolving numbers. Cross-link: lines up with “table numbers are positional, never user-provided” — the invariant is correct but currently leaks into narrative-generation timing.
