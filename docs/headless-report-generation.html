rlm-bmdx · 5dToxReport

Generating reports without the browser

Two ways to take a 5-day study's data files to a finished NIEHS-format report from the command line. Both run the same workflow core as the web UI (workflow/steps.py, ADR-0014) and read and write the same session folder, sessions/<DTXSID>/. A session built one way can be continued the other way, or opened in the browser.

Updated 2026-10-07 Scripts: tooling/generate_report.py · tooling/generate_report_api.sh Examples use PFHxSAm (DTXSID50469320, NIEHS Report 10)
Route A

Python, in-process

One command runs every step and writes the deliverables. No server needed. The only route that builds the LaTeX bundle.

bash
python -m tooling.generate_report DTXSID50469320 \
    --files /data/pfhxsam/* \
    --name "Perfluorohexanesulfonamide" --casrn 41997-13-1 \
    --compound-name PFHxSAm --dose-unit mg/kg \
    --surfaces docx,html,jats,latex,pdf
Route B

HTTP API, with curl

Drives a running server through the same calls the browser makes, in the same order. Use it against a shared or remote deployment.

bash
BASE=http://localhost:9000 tooling/generate_report_api.sh \
    -i DTXSID50469320 -n "Perfluorohexanesulfonamide" \
    -c 41997-13-1 -u mg/kg -k PFHxSAm \
    -s docx,jats,pdf -o output/DTXSID50469320 \
    /data/pfhxsam/*

1The pipeline at a glance

Each step is one Python function and one HTTP call. You never set the workflow phase yourself: it is worked out from which files exist on disk. The green chips show the phase each step moves the session into.

  1. 1
    Import UPLOADED

    Puts the input files into sessions/<id>/files/. Long-format NTP tables are converted to the wide pivot plus a per-animal sidecar.

    Pythoncopy into files/HTTPPOST /api/upload-bm2POST /api/upload-csv
  2. 2
    Validate VALIDATED

    Fingerprints every file and cross-checks doses, animals, sexes and coverage; writes validation_report.json. Any error-severity issue gives VALIDATION_ERRORS instead, and integration is blocked.

    Pythonvalidate_stepHTTPPOST /api/pool/validate/{id}
  3. 2b
    Resolve conflicts optional

    Picks the winning file when two cover the same platform. Without a decision, integration prefers bm2 > txt/csv > xlsx.

    Pythonresolve_stepHTTPPOST /api/pool/resolve
  4. 3
    Confirm metadata

    Accepts or overrides each file's detected platform and data type.

    Pythonconfirm_metadata_stepHTTPPOST /api/pool/confirm-metadata/{id}
  5. 4
    Integrate INTEGRATED

    BMDExpress 3 (Java) merges the pool into integrated.json, the single source of truth for every report section.

    Pythonintegrate_stepHTTPPOST /api/pool/integrate/{id}
  6. 5
    Approve data APPROVED

    Builds the per-animal traceability report, animal_report.json: each animal mapped to dose, sex and core or biosampling selection.

    Pythongenerate_animal_report_stepHTTPPOST /api/generate-animal-report/{id}
  7. 6
    Process minutes when cold

    NTP statistics (Williams, Dunnett, Jonckheere), BMDS modelling, genomics, charts, LLM narratives and Materials & Methods. Every layer is cached, so a repeat run takes seconds.

    Pythonprocess_step (async)HTTPPOST /api/process-integrated/{id}
  8. 7
    Materialize result sections

    Writes the apical result sections as unapproved bm2_<slug>.json drafts.

    Pythonmaterialize_result_sectionsHTTPPOST /api/pool/materialize-sections/{id}
  9. 8
    Background optional

    LLM Background section built from ATSDR, IRIS and PubChem lookups.

    Python--backgroundHTTPPOST /api/generate (SSE) + save-section
  10. 8b
    Summary deterministic · Route A writes it

    Built from the session’s results (most sensitive apical endpoints, gene sets and genes, point of departure); never replaces an approved or hand-written summary.

    Pythonmaterialize_summaryHTTPPOST /api/generate-summary (LLM variant) + save-section
  11. 9
    Render

    Word docx, HTML preview, BITS/JATS XML, Bookshelf-style HTML, Overleaf LaTeX bundle and PDF, all from one document tree.

    Pythonrender_previewHTTPPOST /api/preview/{id}/materialize + GET …/download

bash
python -m tooling.build_published_reports --jobs 3      # or name reports: RR-8 NIEHS-10
python -m tooling.report_qc                             # every report on the shelf

4Route A — Python

One command: tooling.generate_report

bash
cd /workspace/rlm-bmdx
python -m tooling.generate_report DTXSID50469320 \
    --files /data/pfhxsam/*.bm2 /data/pfhxsam/*.txt /data/pfhxsam/*.csv \
    --name "Perfluorohexanesulfonamide" --casrn 41997-13-1 \
    --compound-name PFHxSAm --dose-unit mg/kg \
    --surfaces docx,html,jats,latex,pdf

It imports the files, runs steps 2–7, then renders. Each step prints its result and wall time. A cold run takes several minutes, most of it BMDS dose-response modelling; a repeat run on the same session takes seconds. Deliverables go to output/<DTXSID>/ (or --out):

output/DTXSID50469320/
DTXSID50469320.docx            Word deliverable
DTXSID50469320.html            HTML preview
DTXSID50469320.xml             BITS <book> XML, for Bookshelf submission
DTXSID50469320-overleaf.zip    Overleaf bundle: report.tex + niehs.cls + figures/
DTXSID50469320.pdf             that bundle compiled locally with tect

Options

OptionMeaning
DTXSIDSession id; the folder is sessions/<DTXSID>/. Any DTXSID… id of letters, digits, _ or -.
--files F …Import these files first. Leave it out to use the files already in the session. Adding files to a session that has progressed invalidates its downstream artifacts, as an upload does.
--name, --casrnTest-article identity. Falls back to identity.json, then to the PubChem/CTX resolver (needs network).
--compound-nameShort name for captions and narratives. Default: the identity name.
--dose-unitThe study's dose unit, used on every surface: table headers, Methods, Abstract, Summary, the report’s Appendix B roster and the LLM narratives. State it explicitly. If omitted, the unit the data records is used, else mg/kg, and the log says which. A concentration in air (ppm, ppb, mg/m3) makes it an inhalation study: “exposed to … by inhalation”, “exposure concentrations”, “chamber control”, title “(Inhalation Studies)”, no vehicle or dose formulations.
--metadata FILEClassification overrides keyed by filename: {"organ_weights_truth_male.txt": {"platform": "Organ Weight", "data_type": "tox_study"}}
--design FILEStudy-design facts the data does not record, set on every experiment (as the UI metadata step does) and kept in sessions/<id>/study_design.json, so every later integration (--reintegrate) puts them back: {"strain": "Sprague-Dawley", "administrationMeans": "gavage", "articleVehicle": "corn oil"}. Fields: species, strain, articleRoute, administrationMeans, articleVehicle, studyDuration (controlled vocabulary). A fact the metadata does not record takes the standard design as a fallback: Sprague Dawley rats for five days (studyDuration, e.g. "28d", overrides it), by gavage in corn oil for an oral (mg/kg) unit, by inhalation for an air concentration (ppm), no route fallback for other units. These facts also set the apical table captions: “…of Male Rats Administered X for Five Days”, or “Exposed to X” for inhalation. The log prints NOTE: not recorded in the data, standard design used: …; record the real values with --design whenever they differ. Recorded values that disagree across experiments get no fallback. Facts the data never holds (animal source, quarantine, test-article lot and purity, dose rationale) are a [Placeholder: …] in Materials and Methods, which --strict refuses to ship.
--experiment-metadata FILEExperiment metadata the data doesn't record, as {experiment name: {field: value}} (vocabulary-checked), e.g. {"EDHP mg_kg": {"organ": "liver", "sex": "male"}} for a genomic experiment named by chemical and unit. The fields are laid over the named experiments and kept as the metadata approval (metadata_approved.json), the same record the browser's approval writes, so every later integration re-applies them.
--front-matter FILEFront matter, as the Configure screen saves it to front_matter.json: authors, contributors, publication (report_number, doi, report_date) and strain_designation, the supplier designation the title prints after the strain, e.g. {"strain_designation": "(Hsd:Sprague Dawley® SD®)"}. Keys the file gives replace the saved ones.
--method-profile NAMEThe analysis method profile (profiles/<name>.yaml, ADR-0027). NAME fixes the study on that profile; newest makes it track the newest profile, which is also the default for a study with no pin. A change of profile recomputes. The log prints the profile, unimplemented settings (NOTE) and every setting a .bm2 records differently (WARNING).
--bmd-stats, --go-*GO gene-set table settings for this run, overriding the method profile's (ntp-5day-2025: --bmd-stats fifth_pct,median, --go-pct 5, --go-min-genes 20, --go-max-genes 500, --go-min-bmd 3). Omit them to use the profile.
--reintegrateIntegrate again even though integrated.json exists. Wipes every process cache, so processing starts over. Without it, integration is skipped when integrated.json exists.
--backgroundAlso generate and save the Background section. --model picks the model.
--stop-after STEPvalidate, integrate or process: stop there and render nothing.
--render-onlySkip the pipeline; render the session as it is on disk.
--surfacesComma list from docx, html, jats, bookshelf, latex, pdf. Default docx,html.
--view NAMERender a saved report view (its filters and chart selection).
--strictlatex/pdf: refuse to build while any [… pending] placeholder remains.
--draftRender even when the publish gate is closed (§7).
-vShow pipeline logging, including per-cache provenance events.

The script exits non-zero with the reason when validation finds errors, a step fails, or the publish gate is closed.

Step by step: calling the workflow core yourself

For different wrapping (a batch over many studies, a custom stopping point, extra checks), call the steps directly. This is what generate_report.py does, minus its argument handling. Set up the environment first (§2, or copy _bootstrap_env()): bmdx_pipe reads BMDX_PROJECT_ROOT at import time.

python
import asyncio, shutil
from pathlib import Path

from workflow.store import DiskPoolStore
from workflow.engine import WorkflowEngine
from workflow.steps import (
    validate_step, confirm_metadata_step, integrate_step,
    generate_animal_report_step, process_step, materialize_result_sections,
)
from rendering.preview_surface import render_preview

ID = "DTXSID50469320"
store = DiskPoolStore()

# 1. Import: copy inputs into files/. Validation's disk scan fingerprints them
#    (and converts long-format CSVs), so no upload call is needed.
files = store.session_dir(ID) / "files"
files.mkdir(parents=True, exist_ok=True)
for p in Path("/data/pfhxsam").iterdir():
    shutil.copy2(p, files / p.name)

# 2. Validate: stop on error-severity issues
report = validate_step(ID, store)
assert not [i for i in report["issues"] if i.get("severity") == "error"]

# 3. Confirm metadata: {} accepts what was detected.
#    Keys are file ids from store.get_fingerprints(ID).
confirm_metadata_step(ID, {}, store)

# 4. Integrate (Java)
integrate_step(ID, {"name": "Perfluorohexanesulfonamide",
                    "casrn": "41997-13-1", "dtxsid": ID}, store)

# 5. Approve data: build the animal report
generate_animal_report_step(ID, store)

# 6. Process (async; minutes when cold).  The GO ranking and cutoffs come from
#    the study's method profile; add bmd_stats / go_* keys only to override it.
payload = asyncio.run(process_step(ID, {
    "compound_name": "PFHxSAm", "dose_unit": "mg/kg",
}, store))

# 7. Materialize the apical result sections as section files
materialize_result_sections(ID, store)
print(WorkflowEngine(ID, store).state().to_dict()["phase"])   # APPROVED

# 9. Render: docx gives bytes; html, jats and bookshelf give str
Path(f"{ID}.docx").write_bytes(render_preview(ID, surface="docx"))
Path(f"{ID}.xml").write_text(render_preview(ID, surface="jats"))

The optional Background (step 8) uses the same functions as POST /api/generate:

python
from narrative.chem_resolver import ChemicalIdentity
from narrative.data_gatherer import gather_all
from narrative.background_writer import generate_background

identity = store.read_json(ID, "identity.json")
result = generate_background(gather_all(ChemicalIdentity.from_dict(identity)))
store.save_section(ID, "background", {
    "paragraphs": result["paragraphs"],
    "references": result.get("references", []),
    "citation_report": result.get("citation_report"),
    "abstract_background": result.get("abstract_background", ""),
    "approved": False,
}, archive=False)

For LaTeX, rendering.latex_export provides load_session_data and build_overleaf_bundle. Its standalone CLI (python -m rendering.latex_export --session --dtxsid ID --out bundle.zip) does not apply a saved view's document tree; generate_report --surfaces latex does.

For an interactive run, notebooks/workflow_walkthrough.ipynb runs steps 2–7 one cell each and prints the derived phase after each.

The calls, one by one

The examples assume B=http://localhost:9000 and ID=DTXSID50469320, plus this helper, which only adds the JSON header:

bash
post() { curl -sS -X POST -H 'Content-Type: application/json' --data "${2:-{\}}" "$B$1"; }

1 · Upload

Multipart field files, repeated for several files. .bm2 goes to upload-bm2, everything else to upload-csv. ?dtxsid= saves the files into the session and fingerprints them.

bash
curl -sS -F files=@PFHxSAm_Gene_Expression.bm2 "$B/api/upload-bm2?dtxsid=$ID"
curl -sS -F files=@body_weight_truth_male.csv -F files=@organ_weights_truth_male.csv \
     "$B/api/upload-csv?dtxsid=$ID"
curl -sS "$B/api/wizard/$ID/files" | jq      # what is in the pool now

POST /api/upload-zip (field file) takes one archive instead. DELETE /api/pool/{id}/files/{filename} removes a file (moved to _removed/, recoverable).

2 · Validate

bash
post /api/pool/validate/$ID | jq '{file_count, is_complete,
    errors: [.issues[] | select(.severity=="error")]}'

Any error issue sets the phase to VALIDATION_ERRORS and blocks integration; fix the files and validate again. To choose the winner of a platform conflict yourself, record it before integrating:

bash
post /api/pool/resolve '{"dtxsid":"'$ID'","issue_index":3,"chosen_file_id":"<file_id>"}'

3 · Confirm metadata

{} accepts everything as detected, the same as clicking through the UI panel unchanged.

bash
curl -sS "$B/api/wizard/$ID/fingerprints" \
  | jq -r '.fingerprints[] | [.file_id,.filename,.platform,.data_type] | @tsv'
post /api/pool/confirm-metadata/$ID '{"metadata": {}}'

# override one file:
post /api/pool/confirm-metadata/$ID \
  '{"metadata": {"<file_id>": {"platform": "Organ Weight", "data_type": "tox_study"}}}'

4 · Integrate

The identity is saved as identity.json. To fill one in from the DTXSID alone (best-effort, needs network): post /api/resolve '{"identifier": "'$ID'"}'.

bash
post /api/pool/integrate/$ID '{"identity": {"name": "Perfluorohexanesulfonamide",
  "casrn": "41997-13-1", "dtxsid": "'$ID'"}}' | jq '{experiment_count, bmd_result_count}'

5 · Approve the data

bash
post /api/generate-animal-report/$ID | jq '{total_animals, core_count, biosampling_count}'

6 · Process

The request blocks until processing finishes: minutes when cold, seconds when cached. curl has no default timeout; if a proxy sits in front of the server, check its idle timeout. The response includes base64 chart images, so send it to a file. Everything in it is also cached in the session.

bash
post /api/process-integrated/$ID '{"compound_name": "PFHxSAm", "dose_unit": "mg/kg"}' \
  > process_payload.json

The server takes the GO ranking and cutoffs from the study's method profile. Send bmd_stats, go_pct, go_min_genes, go_max_genes or go_min_bmd only to override it for this run. Leave out dose_unit and the server uses the unit the data records, else mg/kg.

7 · Materialize result sections

bash
post /api/pool/materialize-sections/$ID | jq .materialized

8 · Background optional

POST /api/generate streams Server-Sent Events (progress, then complete or error). Save the result with a second call:

bash
curl -sSN -X POST -H 'Content-Type: application/json' \
  --data '{"identity": {"name": "Perfluorohexanesulfonamide", "casrn": "41997-13-1", "dtxsid": "'$ID'"}}' \
  "$B/api/generate" \
| awk '/^event: /{ev=$2} /^data: /{if (ev=="complete") {sub(/^data: /,""); print}}' > bg.json

post /api/session/save-section "$(jq -c --arg d $ID \
  '{dtxsid: $d, section_type: "background",
    data: {paragraphs, references, citation_report, abstract_background}}' bg.json)"

8b · Summary optional

An LLM synthesis of what the session already holds: the Background, apical result narratives, an approved BMD summary (bmd_summary.json) and any genomics section files. Run it after steps 7 and 8. With none of those present the route returns 400 No approved sections found to summarize, so check for .error before saving.

bash
post /api/generate-summary '{"dtxsid": "'$ID'",
  "identity": {"name": "Perfluorohexanesulfonamide"}}' > summary.json
post /api/session/save-section "$(jq -c --arg d $ID \
  '{dtxsid: $d, section_type: "summary", data: {paragraphs, model_used}}' summary.json)"

Route A writes the Summary itself (workflow.steps.materialize_summary): built deterministically from the BMD summary, the genomics results and the Background’s abstract sentence, saved as an unapproved draft. The calls below are the separate LLM variant.

9 · Render and download

materialize renders the requested surface, plus the HTML view, into sessions/<id>/preview/default/, first moving the previous set into history/. So download each surface right after materializing it.

done
curl -sS "$B/api/preview/$ID/view" > preview.html             # the HTML view

7Approval and the publish gate

A first report needs no approvals. The deliverable renders whatever the session holds. Generated sections render as unapproved drafts; anything not yet produced shows as a visible [… pending] placeholder. --strict refuses a LaTeX build that still has one.

Approval matters once a session is reprocessed. When the data changes, the LLM-written sections are marked stale and block publishing until a person accepts them again. A blocked report gets HTTP 409 from the download route, and Route A refuses to render without --draft.

Accept a section again in Python (the section key is the file stem):

python
from workflow.steps import accept_section_step
accept_section_step(ID, "bm2_body-weight", store)

Or over HTTP. The approve route re-saves the section's current content with the approval stamp:

bash
# a singleton section: background, methods, summary, bmd_summary
data=$(curl -sS "$B/api/session/$ID" | jq '.background')
post /api/session/approve "$(jq -nc --arg d $ID --argjson x "$data" \
  '{dtxsid: $d, section_type: "background", data: $x}')"

# an apical result: section_type "bm2" plus the slug (bm2_body-weight.json → body-weight)
data=$(curl -sS "$B/api/session/$ID" | jq '.bm2_sections["body-weight"]')
post /api/session/approve "$(jq -nc --arg d $ID --argjson x "$data" \
  '{dtxsid: $d, section_type: "bm2", bm2_slug: "body-weight", data: $x}')"

Reopen a section with release_section_step or POST /api/session/unapprove.

8Re-running, caching and resetting

  • Re-running is cheap. Each processing layer is cached by a hash of its inputs, and content preparation is skipped when nothing it depends on changed. A repeat process on an unchanged session takes seconds.
  • Re-integration wipes every process cache, BMDS included, so the next process recomputes from scratch. Route A skips integration when integrated.json exists unless you pass --reintegrate. Route B always integrates. Integration puts back what people stated: the approved experiment metadata (metadata_approved.json) and the --design facts (study_design.json). It also re-pins the method profile when the study tracks the newest one.
  • Adding or replacing a file after validation invalidates the validation report, integrated.json, the animal report and the caches, except the BMDS cache, whose hash comes from the data itself. Approved section text is kept but marked stale.
  • Changing the method profile (--method-profile, or a newer profile for a study that tracks the newest) changes the NTP, BMDS, sections and Methods cache keys, so the next process recomputes them.
  • Reset the pool, keeping identity and sections: POST /api/pool/reset/{id}. Delete the whole session: POST /api/session/reset/{id}. Both are destructive; check the session id first.

ARender surfaces

The report has appendices of its own (A–F). This manual's appendices are referred to as A, B and C, or by section (A.1, B.2, C.3); the report's are always written "the report's Appendix …".

A render surface is one output format of the report. Every surface is a projection of the same two inputs, and none of them is a source of truth. This appendix explains the idea, lists the surfaces, explains BITS and JATS, and says how each surface is checked. It holds as of 2026-10-07.

A.1 The idea: one description, many projections

text

        ▼                                      rendering/latex_export.load_session_data

  • One description. The data assembly and the document tree are shared, so every surface reports the same study: the same sections in the same order, the same tables with the same numbers, rows, footnotes and captions, and the same text.
  • Extract, then emit (ADR-0006). The decision about what a node shows is made once, in render_common, as a plan with no markup in it. Each emitter only turns plans into its own format and applies its own escaping. A bug in what a table contains is therefore fixed once, for every surface.
  • Shared, surface-independent decisions:
    • table and figure numbers, counted by position in the tree;
    • captions, built from the design facts;
    • "not evaluated" statements and [… pending] placeholders;
    • the per-node page breaks and layout styles (styles; see C.2 below);
    • cross-references.
  • Cross-references. Narrative text names a target, not a number ([[xref:bmd-summary]]), so reordering the tree can't leave a stale "Table 3" behind. An unknown target shows as [[xref:??id]], and only table references are wired so far. Each surface resolves the token to its own form:
    • LaTeX: Table~\ref{tab:bmd-summary};
    • HTML: a link reading "Table 8";
    • BITS: <xref ref-type="table" rid="bmd-summary">Table 8</xref>.
  • Outputs are one-way. A surface is never read back. Edits made in Word or Overleaf stay there; the app is not an editor (ADR-0018). The only way in for authored text is a freeform node (C.2 below), which can import a .docx block.

A.3 BITS and JATS

  • JATS, the Journal Article Tag Suite, is the NISO standard XML vocabulary for journal articles (Z39.96). PubMed Central archives articles in it.
  • BITS, the Book Interchange Tag Suite, is JATS extended for books. It adds:
    • book metadata;
    • book parts (chapters);
    • front and back matter;
    • appendix groups.

NCBI's Bookshelf ingests books as BITS. NIEHS's 5-day reports are published there as books: NIEHS-10 is NBK589955. A BITS <book> is therefore the report's ultimate deliverable, and the other surfaces exist for review and editing along the way.

  • the BITS XML;

  • It reproduces the reader content: a contents landing page, one page per section with Previous/Next, tables and figures as thumbnail cards that open in a lightbox, and cross-references that work across pages.

A.5 Limits

BWhat in the report comes from the data

This appendix sets out everything in a report that is driven by the data: the rules (B.1), how each fact is worked out from the files (B.2), where each part of the report comes from (B.3), and where it still falls short (B.4). It holds as of 2026-10-07.

B.1 The rules

  • The integrated dataset is the source of truth. Every number and study fact in the report is read from integrated.json (the BMDExpress project that Integrate builds) and its sidecars, the per-animal files that keep what the pivot drops: cohort (Core or Biosample), observation day, terminal flag and units. Nothing reads the raw .bm2, .txt or .xlsx uploads directly.
  • The document tree sets the structure. Headings, their order and the table and figure numbers come from the template (templates/niehs-5day-report.yaml), or from a saved view's own structure. A study's overlay (templates/studies/<id>/view.yaml) selects what is shown. Numbers are given by position, never typed in.
  • The method profile sets how the data is analysed. The statistical tests, thresholds, BMD acceptance criteria, internal-dose rules, GO ranking and number formats come from the study's pinned profile (profiles/*.yaml, ADR-0027). The footnotes, Methods text and the report's Appendix D that describe the method are generated from those same settings, so the text can't claim a test that didn't run.
  • A fact the data doesn't hold is never invented. It takes one of three forms:
    • a logged fallback (the standard design, the dose unit, an inferred BMR), printed as a NOTE and, for the BMR, footnoted in the report;
    • a visible placeholder ([Placeholder: …], [… pending]) that --strict refuses to ship;
    • "not evaluated", for a data domain the study didn't collect.
  • People supply what no file records. That covers --design, front matter, experiment-metadata approval and section approval. Each is kept in the session and re-applied when integration runs again.

B.2 How the data is read

Each fact below is worked out from the files at the step named. Where a rule is a method setting, the setting's name in the profile is given, with its ntp-5day-2025 value.

Files (Validate, Integrate)

  • What a file is. Each file gets a platform (Body Weight, Organ Weight, Clinical Chemistry, Hematology, Hormones, tissue concentration, clinical observations) and a data type (tox_study, inferred or gene_expression). Confirm metadata (--metadata) can override either. They are detected differently:
    • a .bm2 from its content and chip (ADR-0017);
    • a text or CSV file's platform from NTP naming patterns in its file name, e.g. organ_weights_truth_male.txt.
  • Cross-checks. Validation compares the files with each other: dose groups, sexes, animals and coverage per platform. When two files cover the same data, it asks which one wins. A truth CSV derived from a study workbook is checked value by value against that workbook.
  • Long tables become a pivot plus a sidecar. A one-row-per-animal table becomes the BMDExpress pivot (.txt) that Integrate needs, plus a .sidecar.json. The sidecar keeps what the pivot drops: each animal's cohort, observation day, terminal flag and raw value.
  • Units. Units come from the study workbook's "Key to Column Labels" sheet, or from the .units.json that cebs_to_pool writes. Where both give one, the workbook wins. A unit stated nowhere is left unrecorded and flagged, never assumed. Studies differ: NIEHS-07 to -09 report plasma in ng/mL, NIEHS-10 in µg/mL.

The study (Integrate, then every step)

  • Identity. Name, CASRN and DTXSID come from identity.json. The short name in captions comes from --compound-name.
  • Doses and sexes are read from the files: every file's dose groups and sexes, and the animal report's dose groups.
  • Cohorts. Each animal's Selection says which cohort it belongs to:
    • "Core Animals" are the cohort that every table, statistic and group size is built from.
    • "Biosampling Animals" (NIEHS-10) and "Biosample Animals" (NIEHS-07, -12, -13) are the internal-dose cohort. Both spellings count.
    • A study whose files mark no cohort (NIEHS-02 to -06, RR-8) treats every animal as Core.
    • A database export that marks "Original Animals" uses those, as published.
  • Group sizes for Methods and the N rows:
    • Distinct Core animals are counted per sex and dose across all sidecars.
    • The group size is the most common count over the treated groups. The control size is the most common count over the control groups.
    • Doses with biosampling animals are listed separately ("Additional animals in the … groups").
  • Design facts. Species, strain, route, vehicle and duration come from each experiment's experimentDescription, and every experiment that records one must agree. Integration fills these from the stated design (study_design.json) or approved metadata, else infers them. A fact still missing falls back to the standard design, and the fallback is logged. Values that disagree get no fallback. The standard design is:
    • Sprague Dawley rats for five days;
    • by gavage in corn oil for an oral unit (mg/kg);
    • by inhalation for an air concentration (ppm, ppb, mg/m³).
  • Dose unit. The stated unit wins, else the one unit the data records, else mg/kg (logged). An air-concentration unit changes the wording throughout:
    • "exposed to" and "by inhalation";
    • "exposure concentrations";
    • "chamber control";
    • "postexposure";
    • "(Inhalation Studies)";
    • no vehicle or dose formulations.
  • Wording from the design. Captions are built from these facts, e.g. "Summary of Body Weights of Male Rats Administered Triclosan for Five Days". So are the title's animals and study type, and the Methods animals sentence. Durations up to ten print in words.

Apical endpoints (Process)

  • Derived endpoints:
    • Relative organ weight = organ weight ÷ terminal body weight × 1000 (mg/g), per animal.
    • Body weight gain = last-day weight − first-day weight, per animal.
    • Both get full statistics, LOEL and NOEL, and BMDs.
  • Statistics profile.yaml follow the profile's apical.statistics:
    • A Jonckheere trend test runs on every endpoint.
    • When its p ≤ trend_select_p (0.01), the trend-sensitive pairwise test runs: Williams for weights, Shirley for clinical pathology.
    • Otherwise Dunnett runs for weights and Dunn for clinical pathology (pairwise per platform).
    • Groups smaller than min_group_n (2) are left out.
    • Markers are * at p ≤ alpha (0.05) and ** at p ≤ alpha_strong (0.01).
    • The footnote naming the tests is built from the family that ran.
  • LOEL profile.yaml is the lowest dose with a significant pairwise difference from control, at alpha.
  • NOEL is the highest tested dose below the LOEL. It is "ND" when there is no LOEL or no dose below it, never the control or the top dose.
  • Direction (up or down) is shown only when the trend test is significant.
  • Which rows appear. Every measured endpoint the selections view.yaml keep appears in the tables, whether or not it is significant. N rows count Core animals. The row rules per table are:
    • Body weights: the first and last day, plus any day between that is significant in both the trend and a pairwise test, as NIEHS-12 prints them;
    • Organ weights: each organ has an absolute row (g) and a relative row (mg/g), with terminal body weight as context.
  • Attrition. An animal whose terminal flag falls before the scheduled sacrifice is attrition. Attrition footnotes give the day from the data. Mortality counts Core deaths only, so scheduled biosample sacrifices aren't counted as deaths.
  • Clinical observations. Incidence counts Core animals. The onset of signs is the first day they were recorded. Without clinical-observation data the narrative says nothing about overt toxicity.
  • Decimals. Every mean ± SE in a row prints at one precision, chosen by the endpoint. The precision NIEHS's published summary tables use comes first; an endpoint they don't list uses the precision its values are recorded with (at least one decimal).

Apical BMDs (Process)

  • Where a BMD comes from. profile.yaml
    • The .bm2's BMDExpress results are used where they exist.
    • An endpoint the .bm2 didn't model is fitted with ToxicR Laplace model averaging (apical.bmd.engine) and marked as filled.
    • Where both exist they must agree, or processing stops.
  • Eligibility. profile.yaml A BMD is reported only for an endpoint with a significant trend and a significant pairwise test (eligibility: trend_and_pairwise).
  • BMR. profile.yaml The BMR is the one the .bm2 analysis records. Where it records none, bmr_when_unrecorded (1 SD) is used and footnoted as inferred.
  • Acceptance profile.yaml (acceptance) applies to every BMD, whatever its source. The report's Appendix D-1 prints these values:
    • R² < 0.6, BMD/BMDL > 10, or a BMD above the highest dose → "NVM" (no viable model);
    • a BMD below ⅓ of the lowest nonzero dose → "<LNZD/3".
  • Precision. BMDs print at one precision report-wide: 3 decimals for the NIEHS-10 method (gene expression without gene-level analysis), else 1.

Internal dose (Process)

The rules come from the profile's internal_dose settings profile.yaml, except for the plasma concentration table and the toxicokinetics:

  • Tables are built by study day, from biosample animals.
  • A group with ≤ 20 % of values detected prints "BD" (bd_if_detected_share_at_most). Otherwise values below the limit count as half the limit (below_limit: half_limit).
  • Outliers are removed by the Dixon r10 test at α = 0.01 (outliers).
  • Pairwise markers use Shirley or Dunn, and only when the control has a mean.
  • Values print to 3 significant figures (sig_figs). Normalized rows divide each animal's concentration by its group's nominal dose or exposure concentration.
  • Plasma concentration table (studies with timepoints after dosing, e.g. NIEHS-10):
    • rows are the sampling times ("2 h postdose");
    • columns are the dose groups that have biosample animals;
    • values are the mean ± SE of the biosample animals, with values below the limit of quantification counted as half the limit;
    • it has no statistics or BMDs.
  • Toxicokinetics (tables/toxicokinetics.py) uses the group-mean concentrations at two time points:
    • elimination rate k = ln(C₁/C₂) / Δt and half-life t½ = ln 2 / k, computed only with exactly two time points and a falling concentration;
    • dose proportionality: the high-to-low concentration ratio against the dose ratio;
    • a bioaccumulation flag when t½ > 24 h.

These numbers reproduce NIEHS-10's to the decimal, and the Abstract's internal-dose paragraph reports them.

Transcriptomics (Integrate, Process)

  • Experiments. view.yaml Organ and sex come from each experiment's metadata: approved metadata, else inferred. A view's organs and sex selections choose which organ × sex sections show.
  • Assay. The assay (TempO-Seq, Affymetrix, Illumina) is read from the chip.
  • Sample counts. The sample-counts table counts each experiment's samples per organ, sex and dose.
  • GO tables profile.yaml:
    • They come from the .bm2's GO category analyses.
    • They are ranked by genomics.go_ranking (5th percentile, then median).
    • They are cut by go_display: top 5 %, 20 to 500 genes, BMD ≥ 3.
    • Up and down counts come from the genes' directions.
  • Gene tables. The top genes come from BMDExpress's gene-level (GENE) analysis, sorted by BMD. Fold change is the mean over each gene's probes.
  • Methods. The transcriptomic Methods prompt takes the analysis settings the .bm2 records: version, prefilter, models, BMR and GO filters.
  • Mismatch check. profile.yaml At integration these recorded settings are compared with genomics.recorded (BMR 25 % relative deviation, model averaging). A disagreement is a method_mismatch warning; neither side wins.
  • The report's Appendix C.1 PCA is drawn per tissue and sex from the integrated expression matrix: one dot per animal, coloured by dose. Columns are mean-centred without scaling and decomposed by SVD, with scikit-learn's sign convention. This reproduces NIEHS-10's figures exactly when given the full matrix.
  • Organ order. Genomics sections come one per organ, both sexes stacked: liver, then kidney, then the rest alphabetically.
  • Genomics prose has two layers:
    • an intro and one findings paragraph per organ, built without a model from the ranked tables, using the reliability rules below;
    • the LLM interpretation per organ and sex, grounded in the knowledge base (bmdx.duckdb).
  • Charts. template.yaml view.yaml The UMAP and cluster charts are off: the template's charts: [] matches the NIEHS report, which has no main-body genomics figures. Turned on, clusters are labelled with the study's own GO terms, or with Enrichr terms only if BMDX_ALLOW_ENRICHR=1. New chart types can be declared in the template (chart_types) over the GO table columns, without code.
  • References. The genomics prose may cite only the [Pn] papers it was given, and the Background only its numbered sources. citation_check drops any citation that points at nothing given. The reference list is built from the papers actually cited.

What appears, and where (render)

  • Sections follow the data. template.yaml The template lists every possible section, in order, with its heading and the data it shows. Each one renders with what the session has:
    • a platform the study didn't measure reads "not evaluated";
    • content not yet produced is a visible [… pending];
    • a genomics section appears for each organ the expression data has.
  • Numbering and captions. template.yaml Tables and figures are numbered by their position in the template's tree, and appendix tables per appendix ("Table B-1"). Captions are built from the design facts and the sexes in the data.
  • Views narrow the report without recomputing. view.yaml A study overlay (templates/studies/<id>/view.yaml) or a saved view selects what is shown, and changes neither the data nor the statistics. NIEHS-10's overlay, for instance, keeps the liver-only, male-only organ weight table and the hand-picked "Select" endpoints. The shared template selects nothing, so a study is reported in full unless its overlay says otherwise. The axes are:
    • organs (per area: genomics, organ weight);
    • sex (apical, genomics);
    • assays (clinical chemistry, hematology, hormones; per sex if needed);
    • genes;
    • gene_sets;
    • charts.
  • Page breaks and appendix text. template.yaml The template's styles block sets where pages break, matching NIEHS-10. The report's Appendix C, D and E prose comes from the files the template names (templates/freeform/appendix-{c,d,e}.*). Its Appendix A and F come from the study's own files (templates/studies/<id>/appendix-{a,f}.*), so no other study inherits them.

The animal report and the report's Appendix B (Approve data)

  • The animal report (animal_report.json) traces every animal ID across every file. It has five parts:
    • the study design, as dose × sex × cohort counts;
    • the roster, with each animal's presence per platform;
    • platform coverage;
    • attrition, giving who dropped out and why;
    • sex and dose consistency checks.
  • The report's Appendix B lists each animal with its number, sex, dose and tissue, and the FASTQ name of its expression sample.

The workflow itself

  • Phase. The phase (EMPTY → UPLOADED → VALIDATED → INTEGRATED → APPROVED) is derived from which artifacts exist, never set.
  • Caches. Every cache is keyed by a hash of its inputs: the data, the view and the method signature. A change recomputes only what depends on it.
  • Stale sections. template.yaml When the data changes under an approved section, the section is kept but marked stale, and it blocks publishing until accepted again (§7). The list of sections that need approval is itself derived from the document tree.

Prose built from the data (Process)

  • No model involved. These are assembled from the numbers above, so they can't disagree with the tables:
    • the Abstract (except its Background sentence);
    • the Summary;
    • the Animal Condition, Clinical Pathology and Internal Dose narratives;
    • Methods' Study Design, Dose Selection and Chemistry;
    • the genomics intros and per-organ findings.
  • "Most sensitive" lists in the Abstract and Summary take reliable BMDs only:
    • the BMD must be viable and not NVM;
    • it must be at or above the lower limit of extrapolation (⅓ of the lowest nonzero dose);
    • it must not be anomalous: a BMD below NOEL/10, or LOEL/10 without a NOEL, is left out.
  • LLM-written prose template.yaml profile.yaml is given only the session's numbers, and only through the NIEHS gateway. Genomics narratives may cite only the papers the knowledge base supplies. That prose covers:
    • the apical BMD paragraph;
    • the genomics narratives;
    • the remaining Methods subsections. The template places them and gives their headings; which subsections exist, and when each applies, is fixed in code (SUBSECTION_SKELETON). The Statistical Analysis and apical BMD prompts are built from the profile;
    • the Background.

Rules:

  • The schema is closed.
    • An unknown key, a missing key or an unregistered value fails at load.
    • A profile must state every key. null means "to confirm" and resolves to the built-in default, reported as such.
    • A registered value the tool doesn't implement runs the default and is listed as a deviation (e.g. ntp-5day-2021's BMDS 2.7 engine).
  • Profiles are immutable. A study pins a profile by name and content hash (sessions/<id>/method_profile.json), and an edited profile fails the pin check. A revised method is a new file.
    • A study that tracks its series moves to the newest file automatically.
    • --method-profile NAME fixes a study on one profile.
  • Layers. The built-in default, then the profile, then the study overlay's methods: block, then the request (CLI or UI). A study overlay or request may state any subset of keys. Every resolved value carries its source.
  • Text follows the profile. Footnotes, the Methods statistics and BMD text, and the report's Appendix D-1 are generated from the resolved values.
