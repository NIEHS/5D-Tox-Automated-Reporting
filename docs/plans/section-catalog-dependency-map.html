Section Catalog Dependency Map

Are the workflow's sections created dynamically from the report configuration? Where section identity actually comes from today, every place that duplicates it, and the single catalog that would replace them.

Status: analysis only. No code change described here is implemented. Source of record: docs/plans/section-catalog-dependency-map.md.

No.

The report configuration drives rendering. The workflow's notion of a section (what can be generated, approved, and shown) is hand-maintained in seven places that never read the tree. They agree today only because someone kept them in step by hand.

This note is phase 1: identity. Phase 2, described at the end, traces every downstream dependency of the configured document and needs a document configuration that contains every section currently implemented, so that the traversal covers every path. The user will author that configuration.

1. The finding

The template templates/niehs-5day-report.yaml is instantiated by document_model/document_template.py into the DocNode tree, optionally overridden per session by document_model/document_config.py. That tree drives heading hierarchy, order, table and figure numbering, the table of contents, platform-to-section mapping, and section filtering. All four render surfaces consume it (rendering/report_data.py:455–497, rendering/latex_export.py:893,1111, rendering/preview_surface.py:72).

It does not drive the workflow. What can be generated, what unlocks what, what the session payload carries, and what the Sections screen lists are each a separate literal list. This week's bugs were exactly the places where those lists had drifted:

4. The dependency chain as it exists

5. Proposed: one catalog, derived from the tree

Add document_model/section_catalog.py. It walks the session's tree once and yields the workflow view of it:

@dataclass(frozen=True)
class SectionSpec:
    key: str                  # "background", "methods", "bm2_<slug>", "genomics_<organ>_<sex>", "internal_dose", ...
    node_ids: tuple[str, ...] # tree nodes this section feeds
    kind: Literal["llm", "programmatic", "derived", "authored"]
    producer: str             # dotted name of the generator or deriver; "" for authored
    store: str                # file pattern under the session dir
    approvable: bool
    unlock: tuple[str, ...]   # () | ("processed",) | ("knowledge_base",) | ("background","results")
    instance_of: str | None   # family key for instance sections: "bm2", "genomics"

Where each field comes from

  • key, node_ids, instance_of: from the node's data_key, narrative_key, and platform. Instances expand from data presence exactly as the readiness engine does today, but through the template's platform bindings.
  • kind, producer, store, approvable, unlock: declared on the template node under a new workflow: block, with defaults per node type so existing templates keep working. The dead ready_key field is deleted.

Consumers, in payoff order

  1. R1 readiness takes the catalog instead of its rule dictionary. Instance discovery stays disk-driven, but the family list comes from the catalog.
  2. R4 the session payload iterates the catalog's store patterns. Adding a section to the template adds it to the payload.
  3. R6, R7 the Sections screen renders one route, GET /api/workflow/{id}/sections, carrying the catalog, readiness, and a content summary per key. It dispatches generate and approve by kind and producer. No front-matter list, no prefix special cases.
  4. R2, R3 approve and unapprove validate the type against the catalog and derive the file name from its store.
  5. R5 reset iterates the catalog.

Out of scope because already correct: rendering, numbering, the overlays' content logic, ownership, labels, currency.

Acceptance for phase 1. Internal Dose gains a workflow row, a readiness entry, and a payload field by editing only the template. The 12 existing keys are unchanged. The golden and parity tests stay green.

6. Phase 2: downstream dependencies of the configured document

The catalog fixes identity. What each section depends on at generation time is a second graph, and it can only be traversed against a document that contains every implemented section, otherwise paths stay unexercised.

Input the user provides

A session document configuration, built in the Configure step, enabling every node type and binding the catalog supports: all front-matter parts, the abstract, Background, the full Methods sub-tree including the sample-counts table, all seven apical platforms across the three result sections, the BMD summary, both genomics sections for every organ and sex the data has, Summary, References, plus any freeform pages, freeform blocks, and figures. It runs on a session with genomics data and the knowledge base present.

What phase 2 traces, per catalog entry

  • Data prerequisites. Which processing outputs it reads, and what happens when each is absent: skip, placeholder, or error.
  • Section prerequisites. Approval and content dependencies. Summary reads approved sections; the abstract reads Background and Summary; References reads the genomics caches.
  • Configuration sensitivity. Which per-session values change the output: document structure, report filters by organ, sex, assay, or gene, views, layout style, front-matter metadata.
  • External resources. The model endpoint, the knowledge base, the Java bridge, the chart renderer.
  • Invalidation. Which fingerprint or currency rule re-runs it after a reprocess or a config change.

Method

Run the maximal document through Process, Sections, and Preview with a one-off tracer around the cache reads and the overlays, record the observed reads per section, and diff them against the expected graph. The output is a per-section dependency table plus a list of missed invalidations.

7. Open questions

  • Should instance families (bm2, genomics) be declared in the template as a pattern that expands per data, or stay disk-discovered? Proposal: pattern in the template, expansion by data presence.
  • Does the per-session document config become the source for the catalog, so removing a section also removes its workflow row, or does the workflow always use the full template and treat removal as render-only?
  • The BMD summary is derived but also carries a model-written paragraph. One section with two producers, or two sections?
