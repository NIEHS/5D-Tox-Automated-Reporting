The workflow, the safeguards, and how the new interface uses them

Written 2026-10-24 from the code on ui-redesign (after merging package-layout-workflow-engine at b2916e4). Every name below is a real module, function, file or code; where something is not built yet, it says so.

This document explains, from the bottom up:

  1. the workflow core: what a study is on disk, every step, and the state the workflow derives (phase, legal acts, pins, sections, publish readiness);
  2. the safeguards (safeguards/, ADR-0031): the separate layer that refuses what a person should not do, and explains every refusal in plain words;
  3. the front ends that sit on top: the shared web routes, the command line, the Jupyter notebook;
  4. the new interface: its backend (ui_api/, the /api/v2 routes) and its React/antd front end (ui/), and how each screen reads the derived state and shows the safeguards' refusals.

Three rules hold the picture together:

  • The state is derived, never stored. The phase, the legal acts, a section's readiness, the publish readiness: every one is recomputed from the files in sessions/<id>/ on every call (CONTEXT.md invariant 3). No front end stores or sets any of them.
  • The core holds the invariants; the safeguards hold the idiot-proofing. What must be true for every caller (nothing written is ever lost, a merge either completes or leaves the study as it was, unpublished data never leave for a public model) is in the core. What keeps a person from going wrong (doing a step out of order, letting a machine overwrite their approved text, stating a value outside the vocabulary, shipping a stale report) is in safeguards/.
  • The import direction is one-way. No core package imports safeguards; safeguards imports no front end; nothing below the new interface imports ui_api. Tests enforce all three (tests/unit/test_safeguards_layering.py, tests/unit/test_ui_api_layering.py).

The notebook (notebooks/workflow_walkthrough.ipynb) is the one front end that calls the core directly: it is "the workflow and its code without the idiot-proofing" (the maintainer, 2026-10-14). The browser and the command line go through the safeguards.

Part 1 — The workflow core

1.1 A study is a folder

Everything about a study lives in sessions/<DTXSID>/ (common.paths.SESSIONS_DIR, overridable with the SESSIONS_DIR environment variable). There is no database of sessions and no in-memory state that matters: restart the server and everything is still there. The files, grouped by what produces them:

File Written by What it is
files/ uploads, generate_report.import_files the input data files (.bm2, .txt, .csv, .xlsx and their .sidecar.json)
_fingerprints.json store.ensure_fingerprints one fingerprint per file: platform, data type, file type, hashes, a per-scan file_id
validation_report.json validate_step the file check: issues (each with a severity), the coverage_matrix, is_complete, the fingerprints it checked
precedence.json resolve_step a person's choices between conflicting files
integrated.json (+ integrated.bm2, _category_lookup.json, genomics.sidecar.json) integrate_step the dataset: the merged BMDProject, the single source of truth for every report

Session ids are validated everywhere (common.dtxsid.validate_dtxsid): a bad id never reaches the filesystem (it is what stops /api/session/reset/%2e%2e from deleting sessions/).

1.2 The store

Every step reads and writes through an injected PoolStore (workflow/store.py, ADR-0014): session_dir, read_json/write_json, has_files, artifact_exists, get_fingerprints/ensure_fingerprints, set_integrated, read_section_dicts/read_section_states, has_stale_sections, save_section, archive_section, delete_section. DiskPoolStore is the real one. Tests pass fakes; the new interface's reads pass ui_api.read_model.ReadOnlyDiskPoolStore, which refuses every write (see Part 6).

1.3 The steps, in order

The workflow is thirteen steps (the notebook's numbering). Each core step is a plain Python function: no HTTP, plain arguments, a plain dict back, a workflow.errors.StepError(message, status_code) on failure.

Data preparation

  1. Create the study. A folder with identity.json and meta.json. (In the new interface: ui_api.study_steps.create_study_step, Part 6.)
  2. Bring in files. Uploads land in files/. If the study had already been validated, integrated or approved, the upload calls pipeline.pool_state.invalidate_pool_artifacts (see 1.8): the validation, the dataset, the data approval and the caches go, so the phase falls back. Removing one file (pool_state.remove_pool_file) moves it to _removed/<timestamp>/ (reversible) and invalidates the same way.
  3. Validate — workflow.steps.validate_step. Re-fingerprints every file (a full re-scan), runs bmdx_pipe.validate_pool (cross-file checks, coverage per platform), adds the value-level provenance check (pipeline.value_validation: a derived CSV must equal its source workbook), writes validation_report.json. It never deletes the dataset or the data approval: a validation that finds errors leaves them inert (the phase says so), and one that no longer matches the dataset reads "integrate again". Core refusal: no files/ → StepError(404).
  4. Resolve conflicts — resolve_step appends {issue_index, chosen_file_id, resolved_at} to precedence.json.
  5. Confirm classification — confirm_metadata_step: a person's {file_id: {platform, data_type}} corrections go onto the fingerprints and, for .txt/.csv, into the files' # Platform / # Data Type headers.
  6. Integrate — integrate_step, the heart of data preparation:
    • refuses without fingerprints or a coverage matrix (StepError(400), "run validation first");
    • _check_validation_matches: refuses with ValidationOutOfDate (409) when the fingerprints it would merge no longer match the validation it pairs them with — a file id in the coverage matrix that a cold re-scan re-minted, or files added/removed since. This is a core refusal: going ahead would combine the wrong files;
    • writes identity.json if the caller passed one; reads the test article and any metadata_approved.json (the stated details win over inference);
    • atomic merge: _keep_dataset_files copies the current dataset files aside, bmdx_pipe.integrate_pool merges (Java IntegrateProject; an LLM may infer experiment metadata through the gateway), _check_dataset runs the BMDProject schema over the result; on any failure _restore_dataset_files puts the old dataset back and the step raises StepError(500, "Integration failed: …"). A study is never left "integrated" over a dataset no read accepts;
    • withdraws the data approval (_withdraw_data_approval: animal_report.json moves to history/_data_approval/, never deleted);
    • records the basis (workflow.integration_basis.record_basis);
    • re-applies the stated study design (reapply_study_design) and stamps measurement units onto the sidecars;
    • deletes every Process cache and the query substrate (their inputs changed);
    • compares the dataset's recorded analysis settings with the pinned method profile and writes each disagreement into the validation report as a method_mismatch warning. It pins nothing: the method is a person's choice (C1 D1).
  7. State the facts the data don't carry.
    • Study design: workflow.steps.record_study_design(dtxsid, fields, store) writes study_design.json and puts the fields on every experiment (apply_design_fields), saving integrated.json and re-exporting integrated.bm2. Without a stated design, the report uses the sanctioned standard design and says so in the log (pipeline.study_design).
    • Experiment details: pipeline.metadata_approval.approve_experiment_metadata lays {experiment: {organ, sex, …}} over the descriptions, reconciles the genomics sidecar, re-exports the .bm2 and records metadata_approved.json (which every later integration re-applies).
    • Front matter, abbreviation, the data deposit, the eFDR: command-line helpers.
  8. Data approval — generate_animal_report_step builds the per-animal traceability report (bmdx_pipe.build_animal_report) and writes animal_report.json. Its existence is what the phase calls APPROVED. It informs; it gates nothing (decision Q3): Process is legal from INTEGRATED on.

The report

  1. Process — pipeline.process_integrated.run_process (also as workflow.steps.process_step, and in two halves run_data + run_document/document_step, ADR-0021):
    • _build_process_context calls method_profile.ensure_pin (a study with no pin gets one written pinned_by: "default", tracking the newest profile; a TRACK pin moves to a newer profile) and the definition pin's ensure_pin;
    • concern [1], run_data: NTP statistics, the BMDS/ToxicR modelling, genomics extraction, charts, the BMD summary. Each unit writes _cache_<unit>_<hash>.json, the hash covering every input of that unit, so an unchanged unit is not recomputed;
    • the BMD hard-stop (_BMD_HARD_STOP = True): where both the .bm2 and the ToxicR recompute give a numeric BMD and they differ beyond 25%, the run halts with BmdDivergenceError naming each endpoint and both values;
    • concern [2], prepare_content_if_changed: the prose (genomics narratives, apical BMD narrative, unified narratives, Materials & Methods), skipped when its inputs are unchanged;
    • the payload, then the query substrate (session.duckdb). Every LLM call goes through styling_export.llm_endpoints, whose egress guard raises LLMEgressBlocked for any endpoint but the NIEHS gateway: a core invariant (study data never go to a public model).
  2. Materialize the sections — workflow.steps.materialize_result_sections writes one bm2_<slug>.json per apical platform from the sections cache; materialize_summary writes summary.json (deterministic, narrative.report_summary). Both write through the section write gate (1.7), taking a policy argument (Part 2).
  3. Background (LLM): narrative.data_gatherer.gather_all (PubChem, CTX, ATSDR, IRIS, OSHA/NIOSH, drinking water, mechanism papers, CPDat) then narrative.background_writer.generate_background, saved through the gate.
  4. Review the sections: accept, release, restore, discard (1.7).
  5. Render: rendering.preview_surface.render_preview (html, docx, jats, bookshelf) or the LaTeX/PDF path, from integrated.json + the sections + the document tree.

1.4 The derived state: phase, legal acts, next step

workflow.engine.WorkflowEngine(dtxsid, store).state() gathers presence flags (gather_artifacts: hasFiles, hasStale, the validation report and hasValidationErrors, hasIntegrated, hasAnimalReport, integration, hasQuerySubstrate, hasKnowledgeBase) and returns a WorkflowState: phase, legal_actions, artifacts, completeness, next_step.

The phase (workflow.phases.derive_phase, first rule wins):

# Condition Phase
1 no files in files/ EMPTY
2 no validation_report.json UPLOADED
3 the validation report has an error-severity issue VALIDATION_ERRORS
4 no integrated.json, or one whose basis is out of date VALIDATED
5 no animal_report.json INTEGRATED
6 otherwise APPROVED

A stale section does not move the phase (C1 D2): staleness is a section's matter (its currency and the publish gate).

The integration basis (workflow/integration_basis.py): file ids are not stable (a cold re-scan mints new ones), so "is the dataset still the one this validation describes?" is asked by file name: a SHA over each file's fingerprint minus its volatile fields (file_id, the timestamps), the coverage matrix with ids mapped to names, and precedence.json with ids mapped to names. integration_status answers current, out_of_date (the phase reads VALIDATED), unrecorded (a pre-C1 session: counted as current) or None (no dataset). The engine passes the effective hasIntegrated to derive_phase; the raw flag stays in artifacts.

The legal acts (workflow.phases.LEGAL_ACTIONS, the workflow's own declared table, C1):

Phase Legal acts NEXT_STEP
EMPTY ADD_FILES ADD_FILES
UPLOADED ADD_FILES, REMOVE_FILE, RESET, VALIDATE VALIDATE
VALIDATION_ERRORS the above + RESOLVE, CONFIRM_CLASSIFICATION VALIDATE
VALIDATED the above + INTEGRATE INTEGRATE
INTEGRATED all ten —
APPROVED all ten —

The ten acts (workflow.phases.Action): ADD_FILES, REMOVE_FILE, RESET, VALIDATE, RESOLVE, CONFIRM_CLASSIFICATION, INTEGRATE, STATE_DATASET_FACTS, APPROVE, PROCESS. Why each entry is where it is: ADD_FILES is always legal; VALIDATE stays legal after validation (the cure for an out-of-date integration is "validate again"); RESOLVE/CONFIRM follow a validation and stay changeable after integration; INTEGRATE at INTEGRATED/APPROVED is re-integration (it withdraws the data approval); STATE_DATASET_FACTS writes onto the dataset, so it needs one; PROCESS is not gated on the data approval.

In the core this table is derived state only. No core step checks it. The safeguards enforce it (Part 2).

completeness (compute_section_completeness) turns the coverage matrix into per-platform readiness ("an apical platform needs both study data and a .bm2").

1.5 The pins: the method and the document are fixed per study

The method profile (pipeline/method_profile.py, ADR-0027). A profile (profiles/ntp-5day-*.yaml) declares how the numbers are made: tests, alphas, BMD acceptance, BMR, GO ranking, internal-dose rules. A study is pinned to one in method_profile.json: {name, hash, series, mode, pinned_at, pinned_by}.

  • mode: fixed (pin_profile) or track (track_newest: follows the newest profile of its series).
  • pinned_by: who chose it. ensure_pin writes pinned_by: "default" when a study had none.
  • chosen_by_person(pin): true only for a pin a person made (not default, not absent). This is the fact the safeguards' Process check reads.
  • suggest_profile(dtxsid): the profile to propose: the one of the study's series whose expectations the dataset's recorded analyses contradict least; {name, why}; a read, never applied.
  • A pinned profile whose file changed since pinning raises MethodProfileError("… changed since it was pinned"); an implementation that cannot run here (BMDS 2.7 under Wine, ADR-0030) is substituted and recorded as a deviation.

The document definition (document_model/definition_pin.py, ADR-0029): fixed (the composed definition is snapshotted and rendered from, whatever the templates say later) or track. drift() says how the files have moved away from a fixed pin; a missing or edited snapshot raises DefinitionPinError.

1.6 Sections: catalog, kinds and readiness

The report's sections are derived from the document tree (workflow.section_catalog.catalog_for_tree / catalog_for_session): each SectionSpec has a key, a kind (llm, programmatic, authored), whether it is approvable, its instance_of family (bm2, genomics), its region. validate_section_key refuses a key that is not a section of this report (section_key_invalid).

Readiness (workflow.section_readiness.derive_section_readiness, from KIND_UNLOCK): methods waits for processed; summary waits for the background and at least one results section to be approved; genomics waits for the knowledge_base; the others are always enabled. Recomputed every call: {key: {enabled, blocked_by, approved}}.

1.7 The section write gate and the history

Every write to a section file, a person's or a machine's, goes through workflow.section_writes.write_section(dtxsid, key, content, store, *, act, actor, author, force, reason, cause, status, extra_event, on_owned, review, policy):

  1. the key must be a section of this report (section_key_invalid);
  2. the prior file is read;
  3. unchanged content writes nothing: the content hash (workflow.ownership.content_hash, the dict without its STATE_KEYS: approved, approved_at, facts, stale, regenerated, wording_review, review, revised, version, saved_at) equals the prior's → outcome unchanged, no event. A Process that changed nothing leaves every section file untouched; 4–6. the policy decides what happens over content a person owns. It is called with a WriteRequest and returns None (write), an outcome (hold, knock_down), or raises. With no policy, every write is made;
  4. otherwise the prior file is archived, the new one written with the next version number, and one event recorded.

Rules 1–3 and 7 are core: whoever calls, nothing written is ever lost. Rules 4–6 are the safeguards' policy (Part 2).

The history (pipeline.session_store.save_section): the prior version goes to history/<key>/v<NNNN>-<ts>.json under a name no other archive can take; version numbers are monotonic (one above every version the section ever had, so they never repeat after a discard); each act appends one line (format 2) to history/<key>/index.jsonl: section, version, cause (generate, edit, revise, reprocess, restore, discard, hold), status (draft, working, blessed, needs-re-bless, discarded), act, actor (person/system), author (who wrote the text: generated, model, person, ingested, client), reason, review, changed, content_hash, forced, from_version. section_history and read_version serve them; current_version_status gives the current version's status.

Facts, the ladder and the guard (ADR-0015). A section carries content facts (workflow.labels.Fact): the maturity ladder FIRST_DRAFT → WORKING_DRAFT → FINAL, and the orthogonal PROTECTED. FINAL implies PROTECTED. Facts only move down with a recorded reason (DemoteReason.HUMAN_RELEASE, CURRENCY_FORCED). workflow.guard.GuardLevel (OPEN, GUARDED, PUBLISHED) is the max over the facts.

Ownership — workflow.ownership.is_owned(section), the one predicate: a machine may not replace this text when a person approved it, a person edited it (user_edited), its text came back from outside (source: "ingested"), or it holds FINAL or PROTECTED. workflow.section_writes.is_locked: the stronger condition under which even a person's unforced write is refused (approved, edited, or ingested; a released section is owned but not locked).

The state changes on a section (core steps, workflow/steps.py):

Step What it does Its own answers
accept_section_step approved=True, approved_at, FINAL (+PROTECTED); clears stale, wording_review, review; saved in place (archive=False) with one edit/blessed event against the same version. The text never changes. noop already_accepted when nothing would change; section_not_found, section_key_invalid
release_section_step approved=False, FINAL withdrawn, PROTECTED stays (a released section is still kept from machines); the reason on the event and in revised. noop not_approved
restore_section_step brings a past version back as the next version: not approved, PROTECTED; the current file is archived first; currency markers (stale, review…) carry over from the current file. Takes a policy. noop already_current; version_not_found, version_content_missing
discard_section_step archives, deletes the file, records discard/discarded; restore still reaches it. section_not_found

In the core the reason is optional on all of them. Requiring it is the safeguards'.

1.8 What a data change does to the sections, and the publish readiness

pipeline.pool_state.invalidate_pool_artifacts (called when files change after progress) deletes the validation, the dataset and its sidecars, the data approval, the basis, every cache except the content-hash-keyed BMDS caches, the query substrate and its skip-guard fingerprints. Then, per section (iter_section_files), it asks workflow.reprocess.should_stale_on_reprocess:

  • programmatic sections (bm2_*) are not staled: their numbers refresh;
  • LLM sections that depend on the data (genomics, methods, summary, bmd_summary; not the Background, which is about the chemical) are marked stale: true, regenerated: {reason: "data_changed"}, FINAL withdrawn (demote_for_currency, PROTECTED stays), and saved through save_section with a reprocess/needs-re-bless event (the blessed version is archived).

When Process later materializes an apical section a person approved and its printed content changed, the gate knocks the approval down (C2 D2/A1, section_writes.knock_down): the new content becomes the next version, the approval goes, a review: {why, since_version, flips} marker is set (wording_changed when a categorical data-derived word flipped, numbers_changed otherwise), and a reprocess/needs-re-bless event is recorded. Accepting it again clears it.

Publish readiness (WorkflowEngine.publish_readiness) is derived the same way: workflow.reprocess.blocking_llm_sections lists every LLM section still carrying stale; {can_publish, blocking: [{section_key, reason}]}. Re-accepting a section clears its stale, and it stops blocking.

Part 2 — The safeguards (safeguards/, ADR-0031)

2.1 Why a separate layer

The interface's most important purpose is idiot-proofing (the maintainer, 2026-10-14). Before 2026-10-23 that idiot-proofing had no home: some rules lived in one front end only, some were woven into the core steps, some had no handler and surfaced as a 500. The decision (2026-10-23): a separate layer that front ends go through; it checks the act, explains a refusal in a person's words, then calls the core step. The core keeps the invariants; the notebook calls the core unguarded.

The package:

Module What it guards
safeguards/refusals.py the catalog of every refusal: code, status, plain words, where it is fixed; explain, error_body, register; the refusal classes
safeguards/acts.py whether an act may run now: R6 (session kind), C1 (the phase), the person's method choice, deleting a session
safeguards/sections.py C2: the ownership write policy; reasons
safeguards/inputs.py facts a person states: vocabularies, the dataset's experiments
safeguards/sources.py no Background without its sources
safeguards/publish.py the publish gate
safeguards/guarded.py the one entry point for front ends: the core steps' names and signatures, each with its checks first

2.2 The refusal catalog (safeguards/refusals.py)

The envelope. explain(exc) turns any exception into:

{"error": {"code": "phase_not_allowed", "status": 409,
           "message": "INTEGRATE refused for DTXSID…: the study is in phase VALIDATION_ERRORS (allowed now: …). Fix the validation errors, then validate again.",
           "say": "Combining the files into one dataset isn't possible yet. The file check found errors. Fix what it lists (remove or replace the files it names), then run the file check again.",
           "fix": "files",
           "details": {"action": "INTEGRATE", "phase": "VALIDATION_ERRORS", "legal_actions": [...], "integration": null, "next_action": "VALIDATE"}}}

  • code — from the closed list REFUSALS. A refusal the list does not know is unexpected, never a guess at a nearer one.

  • status — the refusal's own HTTP status when it is a workflow refusal (StepError or one that names its code), else the code's default. An upstream HTTP client's status_code is never taken as this request's.

  • message — the backend's own text, verbatim (for the technical details).

  • say — the plain words, written once, next to the code. Placeholders ({key}, {act}, {sources}, {keys}, {parent}, {species}, {what}…) are filled from the refusal's details and from what a message rule captured; a missing one gets a neutral default (_FIELD_DEFAULTS), never a KeyError.

  • fix — the place in the workflow where the cause is cleared, one of PLACES, or None when nothing a person does clears it ("tell the maintainer"):

    Place Meaning
    study the study itself (which study, its identity)
    files the study's files and the file check
    dataset combining the files into one dataset
    data_review the data review (every animal accounted for)
    method_and_document the analysis method and the document definition

    A front end maps a place to its own screen (Part 6 shows the new interface's map).

  • details — what a screen may show beside the words: the refusal's own details when it names its code, the damaged file's name, a request's field errors, the phase and the legal acts.

How an exception becomes a code (classify):

  1. an exception that carries a code attribute naming a listed code is taken at its word (and its own say/fix, when it knows its case better: the phase guard words each phase differently);
  2. otherwise the first matching _MESSAGE_RULES entry: (exception class name anywhere in its MRO, a regex over the message, the code). For example StepError + ^No fingerprints found → not_validated; StepError + ^Integration failed: → integration_failed (unless the message shows a Java/BMDExpress setup failure → server_setup_failed); GuardViolation + currency BLOCK → stale_content; MethodProfileError + changed since it was pinned → method_profile_changed; LLMEgressBlocked → llm_egress_blocked; InvalidDtxsid → invalid_study_id; UnreadableSessionFile → damaged_session_file; FastAPI's RequestValidationError → bad_request;
  3. otherwise unexpected.

The refusal classes the safeguards raise themselves:

  • PhaseRefusal(dtxsid, action, phase, legal_actions, integration, next_action) — code phase_not_allowed, 409. Its say is "<the act, in words> isn't possible yet." + the phase's own sentence (_PHASE_REFUSAL: EMPTY, UPLOADED, VALIDATION_ERRORS, VALIDATED, and VALIDATED-out-of-date, which says "integrate again"); its fix is the phase's place (files or dataset). Removing a file or resetting in EMPTY says "This study has no files to remove."
  • MethodNotChosen(dtxsid, pin) — method_not_chosen, 409; when a pin exists but was set by default it names it and says it "must be confirmed or changed".
  • Refused(code, message, status_code, details) — any catalog code.
  • StudyRefusal — a Refused for R6 and the study acts.
  • Core classes it explains: StepError, ValidationOutOfDate, SectionRefusal, GuardViolation, the pin errors, LLMEgressBlocked, InvalidDtxsid, UnreadableSessionFile, BMDProjectValidationError.

error_body(exc) — the shape the application's existing routes answer: {"error": message, "code", "say", "fix", "details"} with the status. It is additive: a client that read only error keeps working.

register(codes) — a front end adds its own codes (the new interface's study acts, Part 6). An existing code is never redefined (ValueError); a fix must be a place or None; registering the same definition again is a no-op.

2.3 safeguards/acts.py — whether an act may run now

  • require_data_session(dtxsid, store=None) — R6: no data act on a session whose data is not its own. A companion (published_clone.json) → read_only_session; a report over several studies (studies.json) → report_has_no_data (details: the members). A session that does not exist yet passes (the act's own checks apply). Reads two small files; never creates the folder.
  • require_legal(dtxsid, act, store=None) — C1: derives WorkflowEngine.state() and raises PhaseRefusal when act is not in its legal_actions, naming the phase, what is allowed and NEXT_STEP. Returns the state.
  • require_method_chosen(dtxsid) — C1 D1: MethodNotChosen unless chosen_by_person(read_pin(dtxsid)). Writes nothing.
  • require(dtxsid, act, store=None, *, method=False) — all of them, in order: R6 (every act in Action is a data act), the phase, then, with method=True, the method choice. Only running Process passes method=True (the statistics, the BMDs and the text depend on the method); materializing sections from an existing Process cache does not.
  • require_deletable(dtxsid) — removing a session's folder: never a companion (read_only_session), never one of the studies a report composes (member_of_report, found through document_definition.report_of_member, with the study's key from the report's studies.json). A report session may be deleted: its studies stay.

2.4 safeguards/sections.py — C2: owned content is never overwritten by a machine

ownership_policy(req: WriteRequest) is the write policy the front ends pass to the section write gate. Called only when a write would change the text:

Prior section Who writes Forced? Outcome
absent, or not owned anyone — written (prior archived)

owned system (Process) no apical section with on_owned=REVIEW: knocked down (written, approval withdrawn, review marker, needs-re-bless); any other: held (not applied; a hold event with the held text's hash)

2.5 safeguards/inputs.py — what a person states

  • require_valid_design(dtxsid, fields) — every field must be a design field and every value in its controlled vocabulary (pipeline.study_design.design_field_errors over bmdx_pipe.VOCABULARIES).

  3. the identity: either confirmed (_confirmed_identity: the person ticked the confirmation (identity_unconfirmed), only a looked-up identity is accepted, the name is present (identity_incomplete), a typed CASRN passes its pattern and check digit (invalid_casrn), the lookup still gives the same chemical (identity_changed), and, if the service does not list this DTXSID for the compound, the person said they checked it) — or explicitly pending (_pending_identity: the DTXSID alone; refused if a lookup in the last 10 minutes did find the chemical: confirm it instead);
  4. atomic creation: identity.json and meta.json written in a hidden .creating-… folder, then renamed into place. A rename fails on a non-empty folder, so of two people creating the same study exactly one succeeds; the other gets study_exists. No files, no pins: the phase after is EMPTY.

Filling an identity later (record_identity_step): refuses a missing study, a companion or a report, and an identity already named (identity_exists); the check and the write are one act under a per-study lock (_study_lock), so of two people saving at once one wins and the other is refused.

Deleting (delete_study_dry_run then delete_study_step):

  • the dry run reads only; it lists by plain category what goes (files, sections, dataset, statements, identity, pins, views, runs, log), what stays (the deliverables in output/<id>/, the study's own definition, a report's member studies), the approvals lost and the disk freed; strength: "irreversible"; type_to_confirm = the id; preview_token = a SHA over every path, size and modification time;
  • the delete runs under the study lock: re-runs the dry run (so every refusal holds), checks the typed id (confirm_mismatch; case-sensitive, outer spaces ignored) and the token (changed_since_preview: anything changed after the review refuses), renames the folder out of the store in one step (.deleting-…), forgets what the server holds in memory for it (pipeline.pool_globals.forget_session), then removes it. A study that vanishes mid-read is study_not_found, never a server error.

6.7 The TypeScript: how the screens use all this

The client (ui/src/api/client.ts, errors.ts). Every call resolves with the typed body or rejects with an ApiError carrying the §4.2 body: a non-2xx answer is parsed into the envelope; a body that is not one becomes unexpected; a server that cannot be reached becomes unreachable with its own plain words; a broken run stream has its own. Screens render the error with <Refusal>, never by reading message. noopOf(body) reads a "success that did nothing".

useStudyState(id) (kit/useStudyState.ts) — the only reader of a study's workflow state: a TanStack query on GET …/state. A screen learns the phase, the legal acts, the sections, the readiness and the next step from here only, and never computes, guesses or stores any of them. useStudyMutation(id, fn) re-reads the study's state after every mutating call, whether it succeeded or was refused (a refusal may follow a change made elsewhere). While a run is in flight (once C5 serves run) it polls every 3 s.

<Refusal error|noop studyId> (kit/Refusal.tsx) — the refusal explainer: an antd error Alert with the backend's say first; a link "Go to <module> to fix this" built from fix (kit/modules.ts: module id → title → route /studies/{id}/{slug}); the code, status, verbatim message and details behind "Show the technical details". A noop renders as an info Alert "Nothing was changed". It never shows a bare technical message first.

The modules map (kit/modules.ts): M1 Studies (/studies), M2 Study files (files), M3 Combined data (dataset), M4 Study facts (facts), M5 Method and report definition (pins), M6 Data review (data-review), P1 Process (process), P2 What a change affects (impact), D1 Review the report (review), D2 Written sections (writing), D3 Preview and downloads (preview), D4 Word and Overleaf (handoff), D5 Report setup (setup), D6 Bookshelf (bookshelf). This is how every fix becomes a link.

The study frame (shell/StudyFrame.tsx, StudyHeader.tsx, StudyOverview.tsx, nextStep.ts):

  • the header shows the name, the id, the kind (a companion: "read-only: nothing here is processed or approved", with its twin; a member: "part of a report", with the report; a report: its studies and each one's stage), the stage in plain words (stands.say), and the next step from stands.next as a button to its module; a report names its studies not yet processed;
  • a missing fact (chemical name, CASRN, short name) is a <Pending> mark "[name pending]" whose popover says why and links to the module that fills it: never silence, never a guess;
  • the Steps card lists all ten acts in the workflow's order (kit/words.ts ACTION_ORDER, ACTION_WORDS: plain label, module, destructive). An act in legal_actions is a link to its module; the first legal act of the next step's module is the primary button, tagged "Next"; every other act is visibly disabled with the reason ("Not available now: the study is at "Files checked"."). A phase this page does not know offers nothing. A report and a companion get no Steps card (a report's files are its studies'; a companion is read-only);
  • "What stops the report being published" (kit/PublishReadiness.tsx) lists the readiness items (Blocks / Check, each with its module link); while complete is not true, an empty list reads "Nothing found by the checks below", followed by a warning naming what was checked and what was not (approval of every section, "[… pending]" details, member studies, pins): never "ready to publish" on a partial check;
  • the Method and report definition card shows the pin as the backend reports it: "not chosen" in gold, or the name with "fixed" / "follows the newest", and "chosen by default, not by a person" when pinned_by says so (that study's Process would be refused with method_not_chosen); deviations and unchecked items; the live mismatches as a warning; the definition's source and drift. Never a silent default.

Section marks (kit/SectionStatus.tsx, sectionMark.ts): one tag per section from what the backend serves (stale, regenerated, version status, approved, facts, machine_may_write, the accept verdict); the worst news wins the mark (stale > regenerated > needs re-approval > final > approved > owned > not approvable > waiting > cannot approve yet > draft), the rest is in its tooltip; changed data-derived words are counted and their codes shown as details. Whether a section can be approved is never worked out in the browser: it is accept.allowed.

Fields (kit/VocabField.tsx, IdField.tsx, checkId.ts):

  • a vocabulary field offers only the served values: no free text; a dependent field (strain) is closed until its parent is chosen; a value that no longer fits is flagged, never silently cleared; it never starts with a value the person did not choose; if the vocabularies cannot be loaded, nothing can be chosen. This mirrors on the screen what safeguards.inputs enforces on the server: the screen prevents, the server refuses;
  • an id field checks as it is typed with the backend's pattern, explains why a value is wrong (a suffixed study id, a DOI pasted as a link, a CAS check digit), upper-cases a DTXSID visibly, offers "Use DTXSID…?" for a pasted CompTox address (never fills it without the click), and is never reported good when its rule could not load.

Confirm-or-undo (kit/ConfirmAct.tsx): for an act that changes or destroys something, the consequences come from the backend's dry run, fetched when the person clicks: reversible (done, then Undo), costly (a dialog listing what goes, what stays, the approvals lost, the cost), irreversible (the same, and the person types the study id). An unknown strength is treated as irreversible; if the dry run cannot be had, the act is not offered. A preview_token is passed to the act; changed_since_preview re-reads the dry run and says why. disabled + disabledReason show why an act is not available.

Provenance (kit/Provenance.tsx): every fact a screen shows says where it comes from: Stated, From the files, Inferred, Standard design (assumed), In conflict, with a link to state or settle it; an unknown origin is shown in red as unchecked.

6.8 End to end: the Studies module (built)

S1, the studies list (modules/m1/StudiesList.tsx): one row per chemical from GET /api/v2/studies, its sessions as child rows; each value (kind, stands, next step, format, Bookshelf) is the backend's; a missing name or CASRN is a Pending mark linking to the study; "Create a study" appears only where the backend says can_create. There is no delete in the list.

S2, a new study (modules/m1/NewStudy.tsx):

  1. the DTXSID is typed into an IdField (study id); creation-check says whether the id is free and which format it brings; a refusal (study_id_has_suffix, invalid_study_id) is a <Refusal>;
  2. the chemical is looked up (useChemicalLookup, no automatic retry): an unreachable service (identity_lookup_unreachable) offers "Try again" or creating with the identity pending (PendingCreate); a DTXSID the service does not know (identity_not_found) offers the same;
  3. the person sees the chemical (ChemicalCard: name, CASRN, structure), the format, and must tick the confirmation (and, where the service does not list the DTXSID for the compound, say they checked it); the Create button stays closed until everything required is in;
  4. the create posts confirmed, dtxsid_checked_by_person, format_seen; every refusal of 6.4 comes back as a <Refusal> (study_exists adds an "Open it" button; identity_changed clears the confirmation and re-runs the lookup; format_changed re-reads the creation check and says the format changed).

S3, a study's page (modules/m1/StudyPage.tsx + the shell's panels): the row and its detail, the sessions it belongs with, the workflow panels of 6.7, and the delete card: <ConfirmAct act="delete_study" disabled={!actions.delete.allowed} disabledReason={actions.delete.say}> — so on a companion or a member the button is disabled with the safeguards' own words ("This is the rat study of the report DTXSID1020431. Deleting it would break that report."); otherwise the dry run lists what goes and stays, the person types the id, and the delete presents the token. A study deleted while its page is open reads as "deleted".

6.9 Worked examples: one refusal, all the way through

Process before the method is chosen. A study whose method_profile.json says pinned_by: "default":

  1. its state serves pins.method.pinned_by: "default" and a suggestion; the Method card shows "chosen by default, not by a person";
  2. a Process request reaches safeguards.guarded.run_process → require(dtxsid, PROCESS, method=True) → R6 passes, the phase allows PROCESS, require_method_chosen raises MethodNotChosen;
  3. ui_api.refusals.explain → {code: "method_not_chosen", status: 409, say: "Choose the analysis method … The one it has now (ntp-5day-2021) was set automatically, not chosen by a person, so it must be confirmed or changed. …", fix: "M5", details: {pin: {name, pinned_by, mode}}};
  4. the browser's ApiError → <Refusal> shows the words and "Go to Method and report definition to fix this"; useStudyMutation re-reads the state. The command line prints the same words and the suggested --method-profile.

Integrating while the file check found errors. guarded.integrate_step → require_legal → PhaseRefusal(INTEGRATE, VALIDATION_ERRORS) → say: "Combining the files into one dataset isn't possible yet. The file check found errors. Fix what it lists (remove or replace the files it names), then run the file check again.", place files → module M2.

Process over an approved apical section. guarded.materialize_result_sections passes ownership_policy; the gate sees the printed content changed under an approved bm2_body-weight → knocked down: new version, approval withdrawn, review: {why: "numbers_changed", since_version: 3}, event reprocess/needs-re-bless. The state then serves that section with approved: false, review.say ("The study's data changed the numbers this section prints since it was approved. Read it again, then approve it again."), accept.allowed: true; its mark reads "needs re-approval".

Reopening an approved section without a reason. POST …/sections/summary/release {} → guarded.release_section_step → require_reason → reason_required (400), fix: "D1": "Please say why. The reason is kept with the section's history." Nothing changed.

Deleting a member study. Its row's actions.delete is {allowed: false, code: "member_of_report", say: "This is the rat study of the report …"} from require_deletable; the Delete button is disabled with those words. A direct POST …/delete re-runs the dry run and is refused the same way. The old /api/session/reset route applies the same rule.
